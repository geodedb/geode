# Bug: latest `:dev` (v0.6.26-16) still wedges under load → liveness-SIGKILL(137) crash-loop, **plus** a new `driver: bad connection` mid-batch during sustained ingest

**Status:** **OPEN — reproduced on the latest published `geodedb/geode:dev`** as of
2026-06-10. This is fresh latest-`:dev` confirmation of the *same residual*
`Endpoint.mu` poll-vs-stream contention already tracked in:

- [2026-06-07-unresponsive-under-sustained-query-load-liveness-kill-503.md](2026-06-07-unresponsive-under-sustained-query-load-liveness-kill-503.md) (reproduced there on `0.6.23`) — **same terminal symptom**, and
- [2026-06-03-acceptor-wedge-connection-burst-new-conns-refused.md](2026-06-03-acceptor-wedge-connection-burst-new-conns-refused.md) (root contention) — **same root cause**.

It adds two things the existing reports do not yet capture:

1. **A latest-`:dev` data point** — the wedge + liveness-SIGKILL(137) crash loop
   persists on **`geode v0.6.26-16-gd8c1adb`** (16 commits past v0.6.26), i.e. it
   is *not* fixed in current `dev`. Two independent single-node QA databases
   (`geode-0`, `geode-taxonomy-0`) accumulated **39** and **70** SIGKILL(137)
   restarts respectively before a manual fresh-PVC rebuild.
2. **A new symptom on the WRITE/ingest path** — under a sustained batched-write
   workload (a WoRMS taxonomy seed, `rps=5`, 100-statement batches) geode drops
   the client connection **mid-batch** with `driver: bad connection`
   (`statement 39` of a 100-statement `batch exec`), aborting the ingest. The
   prior reports are read-path (query-load / connection-burst); this is the same
   contention reached on the write path, with a *data-loss* outcome (a partial
   batch) rather than just latency.

> **Update 2026-06-10 (later) — /health mitigation applied; geode then SIGSEGVs (139) instead of liveness-SIGKILL (137).** The QA deployment subsequently adopted the recommended probe split (liveness → out-of-band `httpGet /health:9091`, readiness → in-band `RETURN 1`). This **eliminated the exit-137 liveness-SIGKILLs**, but under the same sustained Playwright e2e load geode then **crashed on its own with SIGSEGV (exit 139)** — a *General protection exception in `readInt` ← `nextMessage`* (the QUIC message parser), restarting ~9× in one run. So the under-load instability is a genuine geode crash, not just probe latency. Full crash stack + analysis: [2026-06-10-sigsegv-readint-nextmessage-under-query-load.md](2026-06-10-sigsegv-readint-nextmessage-under-query-load.md).

## 1. Read-path wedge → liveness SIGKILL(137) crash-loop (STILL OPEN on dev)

`geode-0` terminations are `Reason: Error`, **`Exit Code: 137`** (SIGKILL — *not*
`OOMKilled`, despite the 6Gi limit), i.e. the kubelet liveness probe killed a
`Running` pod whose `RETURN 1` round-trip timed out.

Restart counts observed before the rebuild (single-node, normal QA + e2e traffic,
~23 h uptime): **`geode-0` = 39 restarts**, **`geode-taxonomy-0` = 70 restarts**.

The `proto_reader` stall + degraded QUIC event loop reproduce on `dev` exactly as
in the 2026-06-07 report — examples captured 2026-06-10 under ~13 active
connections during the e2e suite:

```
# idle-stream variant (a long-idle established stream wedges the acceptor):
error: per-stream proto_reader stall: stream_id=0 peer=10.244.2.32 idle_ms=16337061 \
  (this stream wedged while others may still be progressing; restart pod or wait for client retry)
# 16,337,061 ms = ~4.5 HOURS idle before the stall fired — far longer than the
# 65–70 s idle stalls in the 2026-06-07 report; suggests the wedge can also be
# reached by a *long-idle* established stream, not only sustained concurrency.

# under live e2e load (2026-06-10):
proto_reader stall: stream_id=0 peer=10.244.2.59 idle_ms=616913   # ~10 min wedged
quic_first_stream_packet_process_max_ns=1423421657                # 1.42 s to process one packet
quic_active_connections=13
quic_poll_cycle_max_ns=31087484                                   # 31 ms poll cycles
```

**Why it amplifies into an outage:** when the `RETURN 1` probe can't get a QUIC
round-trip inside `timeoutSeconds=8`, liveness fails `failureThreshold=4` times
(~60 s) → kubelet SIGKILLs (137) → ~30–60 s restart+reconnect → every
geode-backed API call (including **user login**) 503s for that window. The probe
added to *detect* the wedge ends up *killing a busy-but-progressing pod*, exactly
as the 2026-06-07 report notes. On a moving `:dev` tag this is continuous: each
kill rolls the StatefulSet, and the cycle repeats.

## 2. NEW: `driver: bad connection` mid-batch under sustained ingest (write path)

During a WoRMS taxonomy seed into `geode-taxonomy-0` (conservative load:
`rps=5`, `sample=500`, 100-statement `batch exec` chunks), geode dropped the
connection **in the middle of a batch**:

```
{"level":"INFO","msg":"seeding from WoRMS (enriched)","rps":5,"sample":500}
{"level":"DEBUG","msg":"flushed chunk","ingested":100}
{"level":"ERROR","msg":"ingest failed","mode":"seed","ingested":100,
 "error":"batch exec (100 statements): geode: statement 39: driver: bad connection"}
```

The first 100-statement batch committed; the second aborted at `statement 39`
with `driver: bad connection` — geode closed/wedged the QUIC stream mid-batch.
This is the **same `Endpoint.mu` contention reached on the write path**, but the
outcome is worse than read-path latency: a **partially-applied batch** and an
aborted ingest (the seed Job failed). A batched writer that loses the connection
mid-batch has no clean way to know which statements committed → at-least-once
replay or a full re-seed is required. (Consistency note for the geode team:
confirm whether `batch exec` is atomic on the server — if the dropped batch is
*not* rolled back server-side, this is a partial-commit/durability concern, not
just a transport flake.)

## 3. Recovery / workaround that worked (2026-06-10)

A **fresh node** survives a bounded active workload even though a long-lived node
wedges:

1. `kubectl delete pvc data-geode-0 --wait=false` then
   `kubectl delete pod geode-0 --force --grace-period=0` → StatefulSet recreates
   `geode-0` with a fresh `data-geode-0` PVC (empty DB).
2. After the fresh node was Ready, a full app reseed (130 users, AT-Proto
   sessions/posts/follows, ~300 entities; ~5 min, sustained writes) **completed**
   — with only **1** SIGKILL(137) restart mid-seed (it recovered and the seed
   finished). I.e. a freshly-restarted node tolerates a ~5-minute active window;
   the wedge manifests against **long-lived** nodes (idle-stream accumulation +
   sustained concurrency), consistent with §1's 4.5-hour idle-stall evidence.

This is only a workaround: on the moving `:dev` tag, long-lived QA/prod nodes
re-accumulate the wedge and resume the SIGKILL(137) crash-loop within hours.

## 3b. Update 2026-06-13 — still reproduces on `v0.6.27-11-g2ac5f12` (includes the inbound-pool starvation fix); acceptor watchdog now converts it to exit(70)

Fresh latest-`:dev` data point from divelife QA (`geode-0`, single node,
normal app traffic, **~23 min uptime** after a clean restart):

- Running build `geode v0.6.27-11-g2ac5f12` — this **includes**
  `0d7d879c` (*accept-time idle clocks + independent inbound sweeper,
  receiver-pool aggregate starvation*), so that fix does **not** close this
  wedge class.
- Same per-stream wedge signature: `per-stream proto_reader stall:
  stream_id=0 peer=10.244.2.174 idle_ms=…` climbing from ~60 s to **417 s**
  (the peer is the `divelife-api` pod), in-band `RETURN 1` readiness timing
  out along the way.
- The 2026-06-05 acceptor watchdog **worked as designed**: `ACCEPTOR WEDGE:
  :3141 UDP rx_queue=9448031 bytes stayed >= 8388608 for >= 30000ms` →
  self-restart **exit code 70** (no more liveness-SIGKILL-137 — QA liveness
  is the out-of-band `/health:9091` split). End-to-end outage was still
  ~9–10 min: ~7 min of per-stream stall before the rx_queue crossed the
  watchdog threshold, then restart + client reconnect.
- Downstream amplification noted for operators: clients (api/pds) whose
  k8s liveness probes check geode-dependent `/healthz` get SIGKILLed during
  the stall phase and re-enter CrashLoopBackOff (up to 5 min kubelet
  backoff), extending the user-visible outage past geode's own recovery.
  Mitigation shipped app-side (dependency-free `/livez` liveness split).

The per-stream stall watchdog (#864 §10) observed the wedge for ~7 minutes
but is deliberately log-only. Given the stalled stream held `RETURN 1`
readiness down (traffic already shed) for the whole window, a third concrete
ask:

3. **Self-restart (or stream-abort) on prolonged per-stream stall when the
   in-band readiness query is also failing** — if `RETURN 1` cannot complete
   for N consecutive probes *and* a stream has been stalled past the
   threshold, the "may be mid-transaction" caution loses its force; an
   earlier exit(70) would have cut ~6½ minutes off this outage.

## 4. What would actually fix it (pointer)

Per the existing reports, eliminating the wedge requires reworking the QUIC
dependency's **poll-vs-accept / `Endpoint.mu` locking** (§7 of
2026-06-03-acceptor-wedge…). The watchdog (`exit 70`) + the `RETURN 1` probe
turn the wedge into an auto-restart instead of a manual outage, but they do not
prevent it, and on the read path the probe itself is now the killer (§1). Two
concrete asks for the geode team from this latest-dev repro:

1. **Idle-stream reaping:** a stream idle for minutes→hours (idle_ms up to
   16.3 M ms observed) should not be able to wedge the acceptor for *new*
   connections. An idle-stream timeout / reaper independent of the
   poll-vs-accept lock would cut off the §1 idle variant.
2. **`batch exec` atomicity under mid-batch disconnect:** confirm/guarantee the
   server rolls back a batch whose stream drops mid-flight (§2), so a writer
   that retries doesn't double-apply the committed prefix.
