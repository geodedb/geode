# Bug: acceptor wedges at **near-zero load** on production v0.6.26, and both stall watchdogs miss it — 94 minutes of hard downtime before self-restart

**Status:** **OPEN — observed in production** on the pinned release image
`geodedb/geode:0.6.26`, 2026-07-26. 23 restarts on one StatefulSet pod.

This is the same `Endpoint.mu` acceptor wedge already tracked in:

- [2026-06-03-acceptor-wedge-connection-burst-new-conns-refused.md](2026-06-03-acceptor-wedge-connection-burst-new-conns-refused.md) — root contention, and the report the acceptor watchdog was built for.
- [2026-06-10-dev-v0.6.26-still-wedges-plus-batch-ingest-bad-connection.md](2026-06-10-dev-v0.6.26-still-wedges-plus-batch-ingest-bad-connection.md) — v0.6.26 dev confirmation.
- [2026-06-21-sustained-single-conn-ingest-wedge-checkpoint-rwlock-deadlock.md](2026-06-21-sustained-single-conn-ingest-wedge-checkpoint-rwlock-deadlock.md) — a wedge on one connection.

It adds three things none of those capture, and the second is the actionable one:

1. **The wedge does not need load.** Every prior report reproduces under sustained
   query load, a connection burst, or a batched ingest. This pod read
   **54,972 bytes total in the 73 minutes before it wedged** — a near-idle
   service with a handful of health-check connections. Load is not the trigger.
2. **Both stall watchdogs failed to catch it promptly, for different reasons, and
   the service was hard-down for 94 minutes.** Detection is volume-based where it
   needs to be progress-based. Details in §3 — this is the fix worth making.
3. **`proto_reader_bytes_read_total` freezing is an exact, already-emitted wedge
   signal.** It froze 28 seconds before the first dependent lost readiness, and
   94 minutes before the watchdog acted. The signal to act on is already in the
   metrics stream.

## 1. Timeline of one wedge (exact, from container logs)

The metrics line is emitted every 5s and **kept being emitted throughout**, so the
process stayed alive and the metrics thread kept running. Only the read path
stopped.

| Time (UTC) | Event |
|---|---|
| 18:44:19 | container starts; `server ready (694ms total)`, QUIC listening on :3141 |
| 18:44:25 → 19:57:37 | normal operation. `proto_reader_bytes_read_total` climbs to **54972** |
| **19:57:37** | **`proto_reader_bytes_read_total` freezes at 54972 and never changes again.** Wedge onset. |
| 19:58:05 | `mentats-server` readiness fails — `/readyz` 503. **28s after onset.** Dependent hard-down from here. |
| 19:58 → 21:31 | 1,128 further 5s metrics lines, **every counter identical**. No log line of any kind other than the frozen metrics. |
| **21:31:37** | acceptor watchdog finally fires, `exit 70`, pod restarts, service recovers |

**Downtime: 19:58:05 → 21:31:39 ≈ 93.5 minutes**, all of it after geode had
already emitted, every 5 seconds, an unambiguous signal that it was wedged.

The frozen counter set at the moment of the wedge:

```
proto_reader_messages_delivered_total=907
proto_reader_would_block_loop_iterations_total=403
proto_reader_bytes_read_total=54972
proto_reader_eof_total=455
quic_response_messages_started_total=1359
```

`would_block_loop_iterations_total` also freezes, which is the tell: the reader is
not spinning on `WouldBlock`, it is **not running at all**. It is blocked, not
looping.

The terminating line:

```
error: ACCEPTOR WEDGE: :3141 UDP rx_queue=8432640 bytes stayed >= 8388608 for >= 30000ms
  — the QUIC acceptor is wedged and not draining new connections. Self-restarting so
  the orchestrator recovers automatically (set GEODE_ACCEPTOR_WATCHDOG_DISABLE=1 to opt out).
```

## 2. What this says about the wedge itself

- Not load. 54 KB read across 73 minutes.
- Not OOM, not SIGKILL, not SIGSEGV. Clean watchdog-initiated `exit 70`.
- Not a downstream handler stall in the sense of #864: there were **no active
  stream handlers** at wedge time (see §3), so nothing was stuck mid-query.
- The process, its metrics thread, and its 5s timer all keep running. Only the
  socket read path is dead.

That combination points at the acceptor/poll path taking `Endpoint.mu` and never
releasing — consistent with the RC-A contention in the 2026-06-03 report, but
reached with essentially no traffic, which the existing reproductions do not
cover. A wedge that needs no load is a much better reproduction target: whatever
ordering causes it is reachable from a handful of idle health-check connections
rather than requiring a burst.

## 3. The actionable defect: both watchdogs miss an idle wedge

There are two watchdogs in `src/server/main.zig`, and this incident slips between
them.

### Watchdog A — `#864` proto_reader stall watchdog (~line 2755)

```zig
const idle_ns = proto_reader_metrics.getIdleNs();
const pending = quic_connection_handler.getGlobalStreamThreadCount();
if (idle_ns >= stall_threshold_ns and pending > 0) {
```

This watches exactly the right variable — reader idleness — but gates on
`pending > 0`, i.e. it only alerts when handlers are wedged *downstream* of
`nextMessage`. Here the reader itself was wedged with **no** in-flight handlers,
so `pending == 0` and the condition never held. The comment above it explains the
gate ("a single intentionally-idle multiplexed connection" must not false-positive),
which is reasonable — but it means an idle-time wedge is indistinguishable from a
legitimately idle server *by this predicate alone*.

It also only logs; it never restarts.

### Watchdog B — accept-path wedge watchdog (~line 2794)

```zig
// src/server/acceptor_watchdog.zig
pub const default_rx_threshold_bytes: u64 = 8 * 1024 * 1024; // 8 MiB
pub const default_deadline_ms: i64 = 30_000;
```

This one does restart, and it did — but it triggers on **accumulated volume**:
`rx_queue >= 8 MiB` held continuously for 30s. At this pod's traffic rate, filling
the 8 MiB socket buffer took **94 minutes**. The 30s deadline is irrelevant; the
8 MiB threshold is the latency. The busier the service, the faster this fires —
which is exactly backwards from what you want, because it means the quietest
services suffer the longest outages.

### The gap, stated plainly

> A wedged reader with no pending handlers and low traffic is invisible to
> Watchdog A (looks idle) and takes `8 MiB / arrival-rate` to reach Watchdog B.

### Suggested repair

Make the trigger progress-based rather than volume-based. The disambiguating fact
that separates "idle" from "wedged" is not queue depth, it is **whether there is
unread data the reader is not consuming**:

```
wedged  ==  rx_queue > 0  AND  proto_reader_bytes_read_total unchanged  for >= deadline_ms
idle    ==  rx_queue == 0  AND  bytes_read unchanged
```

Both terms are already available at the callsite — `readListenerRxQueue(ctx.quic_port)`
and the reader counters are read in the same 5s tick. Two options, either of which
would have cut this incident from 94 minutes to ~30 seconds:

1. **Preferred — add a second trigger to Watchdog B.** Keep the existing 8 MiB
   volume trigger as a backstop and add: restart when `rx_queue > 0` and
   `proto_reader_bytes_read_total` has not advanced for `deadline_ms`. Needs one
   extra piece of tracker state (last observed `bytes_read` + timestamp) in
   `acceptor_watchdog.zig`, and it stays a pure function of values already polled.
2. **Or — relax Watchdog A's gate** from `pending > 0` to
   `pending > 0 or rx_queue > 0`, and give it the same self-restart path.
   `rx_queue > 0` is what makes it safe against the intentionally-idle
   false positive the current gate exists to prevent.

A non-zero floor (e.g. `rx_queue >= 1 datagram`) avoids restarting on a single
stray packet, and the deadline already provides hysteresis.

Worth considering alongside: expose `udp_rx_queue_bytes` in the metrics line. It
is polled every tick for the watchdog but is not in the snapshot, so from logs
alone you cannot see the queue growing — the only reason this report can time the
wedge is that `bytes_read` happens to freeze.

## 4. Reproduction hypothesis (untested)

Because load is not required, the cheapest reproduction attempt is probably:
single node, QUIC + TLS, one client that opens a connection, issues a trivial
query (`RETURN 1`) on a ~10s interval and lets each connection reach EOF —
mirroring a Kubernetes readiness probe. Note `proto_reader_eof_total=455` against
`messages_delivered_total=907`: roughly one EOF per two messages, so this workload
is dominated by short-lived connections closing, not by streaming. If the wedge is
an accept/teardown ordering bug on `Endpoint.mu`, probe-shaped connection churn is
the likeliest trigger, and it would explain why an otherwise-idle production node
hits this every few hours.

Observed inter-wedge interval on this pod: the run documented here lasted 2h47m
(18:44:19 → 21:31:37).

## 5. Operator-side mitigation available today

Until the detection fix lands, shrink the volume threshold so the existing
watchdog fires sooner on quiet nodes:

```
GEODE_ACCEPTOR_WATCHDOG_RX_BYTES=131072   # 128 KiB instead of 8 MiB
GEODE_ACCEPTOR_WATCHDOG_DEADLINE_MS=30000 # unchanged
```

At this pod's rate that is roughly a 1–2 minute detection instead of 94. This
trades a small false-positive risk under genuine bursts for a large reduction in
wedge downtime; it is a mitigation, not the fix, because the correct predicate
still is not "how much is queued".

Do **not** set `GEODE_ACCEPTOR_WATCHDOG_DISABLE=1` on a node that exhibits this —
the watchdog is currently the only thing recovering the service.
