## Bug A — QUIC DNS resolver does not apply resolv.conf `search` domains

**Symptom:** with `GEODE_PEERS=geode-0.geode:4242,…` (headless short names):

```
WARN geode.raft raft transport getOrCreatePeerConnection failed error=InvalidAddress peer=2
```

**Root cause:** `resolveHostToIp()` (`src/transport/quic.zig:1397`) does
`dns.Client.resolveA(host)` (`:1414`) and returns `error.InvalidAddress` (`:1415`)
on failure. This custom resolver issues a bare A lookup with **no `search`-domain
expansion**, so `geode-0.geode` → NXDOMAIN even though the pod's glibc resolver
(`getent hosts geode-0.geode`) succeeds via the `search geode-qa.svc.cluster.local …`
list.

**Workaround (proven):** use FQDNs —
`geode-N.geode.<namespace>.svc.cluster.local:4242`. The `InvalidAddress` errors
clear and the failure advances to Bug B.

**Suggested fix:** in `resolveHostToIp`, fall back to the system resolver
(getaddrinfo / `std.Io.net`, which honors `search`) or apply the resolv.conf
search list before returning `InvalidAddress`. Document that k8s peers must be
FQDNs until then.

## Bug B — Raft election never converges between distinct pods (BLOCKER)

**Symptom:** with FQDN peers (Bug A worked around) **and** the TLS handshake
completing — confirmed by setting `GEODE_CLUSTER_INSECURE=1`, which the release
image honors here and which clears all `HandshakeError` — all three nodes still:

```
[raft] node 1 state=candidate term=0 iter=2500
[raft] node 2 state=candidate term=0 iter=2700
[raft] node 3 state=candidate term=0 iter=4400
```

No transport errors, peers connect, **but `term` never advances past 0 and no
leader is elected.** This is the same terminal state GAP-0838 describes, reached
*after* the handshake is no longer the blocker — so there is a **second,
election-layer defect** distinct from the TLS transcript bug. The GAP-0838
regression test (2-node loopback handshake) does not cover real RequestVote /
term-advance / leader-election across distinct pods, which is why it passed while
this fails.

**Where to look:** `src/distributed/raft_consensus.zig` (RequestVote send/recv,
term advance, vote tally), `src/distributed/cluster.zig` (`sendToNode`
`findNodeEndpoint`, the tick/election loop). Worth checking whether RequestVote
RPCs are actually delivered+counted cross-pod (cluster-token frame auth, the
`0xAAAA…` uninit `node_id` seen in `Node detected as failed` logs) vs. silently
dropped.

**Note on the insecure path:** `GEODE_CLUSTER_INSECURE=1` is documented as
refused in release builds, but the published 0.6.14 image accepted it here
(handshake bypassed). Either the gate isn't effective in this build or the path
differs from `cluster_auth.isInsecureModeAllowed()` expectations — worth a look.

## TLS trust (for when Bug B is fixed) — k8s cert requirements

The cluster QUIC listener auto-generates a **per-node self-signed** cert
(`cluster.zig:504`, `cert_gen.ensureCertificatesAtPath`), so the default
(verified) path `HandshakeError`s because peers share no CA. The secure path
needs `GEODE_CLUSTER_CA_CERT` (`cluster.zig:1974`, `raft_consensus.zig:874`)
pointing at a CA that signed all members, with the leaf SANs covering the
headless pod DNS names. On k8s that means an **internal cert-manager CA** (public
CAs can't sign `*.svc.cluster.local`), and clients must then trust that CA. This
is the "document the required server cert SANs + CA env for Kubernetes" item from
GAP_ANALYSIS line 66 — still unmet.

## Resolution (2026-06-02)

### Bug A — FIXED (code defect)

Root cause confirmed at the code level: the bundled `dns` library
(`dns-0.1.9`) runs in stub mode and resolves the hostname **verbatim** — it
has *no* resolv.conf `search`/`ndots` support whatsoever. So `geode-0.geode`
NXDOMAINs while glibc's `getaddrinfo` (which appends the `search` list)
succeeds.

Fix: new pure, std-only module `src/transport/dns_search.zig` implements the
glibc stub-resolver candidate algorithm — parse `search`/`domain`/`options
ndots:N`, then build the ordered candidate list (search-expanded names first
for short names under `ndots`, bare name first once the name already has
`>= ndots` dots, absolute for a trailing-dot name). `resolveHostToIp`
(`src/transport/quic.zig`) now reads `/etc/resolv.conf` and tries each
candidate until one resolves. On any resolv.conf read failure it falls back to
the bare host name, so non-k8s environments are unchanged. Unit tests:
`zig build test-dns-search` (7/7).

### Bug B — ROOT-CAUSED + HARDENED (environment/contract, not a consensus defect)

Verified at the code level that the raft pure logic (pinned `raft-0.1.4`
`handleRequestVote` echoes `pre_vote` in every branch; `handleRequestVoteResponse`
counts by `from` + `pre_vote`) and the geode protobuf wire bridge
(`pre_vote`/`vote_granted`/`from` all round-trip — the prior "A6d" fix) are
**correct**. A real 3-node cluster of `geode serve` processes on loopback (same
config as `tests/test_cluster_3node_subprocess.zig`) **elects a leader** (node
reaches `state=leader term=2`, the other two `follower term=2`). So the stuck
`candidate term=0` state is **not** a defect in consensus, serialization, or
auth — it is a violation of the cluster **identity contract** specific to the
k8s deployment:

> Every node derives each peer's raft id from its **1-based position** in the
> shared `GEODE_PEERS` list, and stamps its OWN `GEODE_NODE_ID` as the `from`
> on the frames it sends. If `GEODE_NODE_ID` ≠ this node's position, peers
> reject its RequestVote responses as "from a non-voter" (silently, inside the
> raft lib) → it hangs at `candidate term=0`. With loopback IP peers the
> bootstrap self-identifies by `(host, port)`; with k8s DNS names that
> host-skip never fires, so correctness rests *entirely* on `GEODE_NODE_ID`
> matching position. The `0xAAAA…` node id in `Node detected as failed` logs is
> a downstream symptom (the health loop evicts peers once heartbeats stop).

The `GEODE_CLUSTER_TOKEN` check is also enforced even under
`GEODE_CLUSTER_INSECURE=1`; an unset/mismatched token silently drops every raft
frame (same `candidate term=0` symptom).

Hardening landed (purely additive — does **not** change which peers are
configured): `src/server/cluster_identity.zig` is a boot-time identity-contract
self-diagnostic, wired into `cluster_bootstrap.maybeStart`. It compares the
pod's `$HOSTNAME` (forwarded from `main.zig`) against the `GEODE_PEERS` entries
and emits a loud, actionable `[cluster-identity]` line on stderr (visible in
`kubectl logs`) **before** the doomed election. On the exact failing config it
now prints:

```
[cluster-identity] ERROR: GEODE_NODE_ID does not match this host's 1-based
position in GEODE_PEERS. ... the cluster will hang at 'state=candidate term=0'.
Set GEODE_NODE_ID to the position shown. (node_id=1, configured_peers=3,
self_skips=1, voter_peers=2, this_host_position=2)
```

It also flags `node_id` out of range (0 or > N), no self entry skipped, and an
informational reminder for any DNS-named cluster. Unit tests:
`zig build test-cluster-identity` (7/7). Healthy loopback 3-node election still
converges (regression-checked); the diagnostic stays silent on healthy configs.

**Operator action for k8s 3-node:** set `GEODE_NODE_ID` to the pod ordinal **+
1** (`geode-0` → `1`, `geode-1` → `2`, `geode-2` → `3`), ship a byte-identical
`GEODE_PEERS` list (FQDNs until Bug A's image ships, then short names work too),
and ensure a matching `GEODE_CLUSTER_TOKEN` on every pod even when running
`GEODE_CLUSTER_INSECURE=1`.

## Resolution (2026-06-03) — Bug B FIXED: auto-derive node_id

The diagnostic from the 2026-06-02 pass named the contract but still required the
operator to set `GEODE_NODE_ID` correctly. Follow-up #1 is now implemented so the
cluster forms itself.

`src/server/cluster_bootstrap.zig` resolves the node's raft id from its
**`$HOSTNAME`** rather than trusting a hand-set `GEODE_NODE_ID`:

- `computeSelfIdentity(specs, $HOSTNAME)` → the 1-based position of the peer
  entry whose host matches `$HOSTNAME` (exact or leading-label, via
  `cluster_identity.hostMatchesSelf` — `geode-1` matches
  `geode-1.geode.…svc.cluster.local`), plus whether any peer is a DNS name.
- `resolveNodeId(explicit, self_position)` makes the hostname position
  **authoritative** (it is the id every peer assigns this node):
  - `GEODE_NODE_ID` unset + hostname match → **derive** the id (a StatefulSet
    needs no `GEODE_NODE_ID` at all);
  - `GEODE_NODE_ID` set but ≠ hostname position → **override** to the hostname
    position and log a `WARN` (instead of silently hanging at `term=0`);
  - no hostname match → fall back to the explicit `GEODE_NODE_ID` (loopback /
    non-k8s, unchanged);
  - neither → `MissingNodeId` (unchanged).

With `node_id` == position, the existing position-based self-skip and the
`from`-stamping on outgoing frames line up, so `RequestVote`/`RequestVoteResponse`
frames are no longer dropped as "from a non-voter" and the election converges.

**Tests:** `zig build test-cluster-bootstrap` — 8 pure-helper cases (derive /
agree / override / loopback-fallback / none; hostname-label match; loopback &
empty-hostname) + 2 end-to-end `maybeStart` cases (derive with no `GEODE_NODE_ID`;
override a mismatched one). `zig build test-cluster-3node-election` and
`test-cluster-3node-subprocess` confirm a loopback 3-node cluster still elects a
leader (the explicit-`GEODE_NODE_ID` path is unchanged).

**Operator action (k8s 3-node) is now optional:** ship a byte-identical
`GEODE_PEERS` (short headless names work post-Bug-A) and a matching
`GEODE_CLUSTER_TOKEN` on every pod; `GEODE_NODE_ID` may be omitted (derived from
`$HOSTNAME`) or, if set, will be auto-corrected to the hostname position.

**Residual:** a true DNS-resolved multi-pod election can only be validated in a
real cluster (peers must resolve); the in-repo coverage is the pure-resolver
unit tests + the loopback election regressions. Re-enable the 3-node kustomize
component in `geode-argo-arda` to validate end-to-end on the arda cluster.
