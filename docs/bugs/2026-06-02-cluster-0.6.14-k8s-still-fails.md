# 0.6.14 cluster: 3-node k8s StatefulSet still fails to form (two new bugs past GAP-0838 TLS fix)

**Date:** 2026-06-02
**Image:** `geodedb/geode:0.6.14` (== commit `a69cd6ae`, which DOES contain the
GAP-0838 tls-v0.1.9 CertificateVerify fix)
**Environment:** arda cluster (`company.arda-ca.net`, bare-metal/flannel,
`local-path` storage), namespaces `geode-qa`/`geode-prod`, real 3-replica
`StatefulSet` with headless-service peer DNS.
**Relationship to GAP-0838:** GAP-0838's fix was validated only with a **2-node
TLS handshake on loopback IPs (`127.0.0.2`)** + a real CA cert
(`tests/test_gap0838_cluster_tls_noloopback.zig`). That test never exercises
(a) DNS-based peer addressing or (b) actual multi-node Raft election. Both fail
in a real k8s deployment. **Result: a 3-node cluster still does not elect a
leader on 0.6.14.**

---

## Bug A — QUIC DNS resolver does not apply resolv.conf `search` domains

**Symptom:** with `GEODE_PEERS=geode-0.geode:4242,…` (headless short names):

```
WARN geode.raft raft transport getOrCreatePeerConnection failed error=InvalidAddress peer=2
```

**Root cause:** `resolveHostToIp()` (`src/transport/quic.zig:1397`) does
`dns.Client.resolveA(host)` (`:1414`) and returns `error.InvalidAddress` (`:1415`)
on failure. This custom resolver issues a bare A lookup with **no `search`-domain
expansion**, so `geode-0.geode` → NXDOMAIN even though the pod's glibc resolver
(`getent hosts geode-0.geode`) succeeds via the `search geode-qa.svc.cluster.local …`
list.

**Workaround (proven):** use FQDNs —
`geode-N.geode.<namespace>.svc.cluster.local:4242`. The `InvalidAddress` errors
clear and the failure advances to Bug B.

**Suggested fix:** in `resolveHostToIp`, fall back to the system resolver
(getaddrinfo / `std.Io.net`, which honors `search`) or apply the resolv.conf
search list before returning `InvalidAddress`. Document that k8s peers must be
FQDNs until then.

---

## Bug B — Raft election never converges between distinct pods (BLOCKER)

**Symptom:** with FQDN peers (Bug A worked around) **and** the TLS handshake
completing — confirmed by setting `GEODE_CLUSTER_INSECURE=1`, which the release
image honors here and which clears all `HandshakeError` — all three nodes still:

```
[raft] node 1 state=candidate term=0 iter=2500
[raft] node 2 state=candidate term=0 iter=2700
[raft] node 3 state=candidate term=0 iter=4400
```

No transport errors, peers connect, **but `term` never advances past 0 and no
leader is elected.** This is the same terminal state GAP-0838 describes, reached
*after* the handshake is no longer the blocker — so there is a **second,
election-layer defect** distinct from the TLS transcript bug. The GAP-0838
regression test (2-node loopback handshake) does not cover real RequestVote /
term-advance / leader-election across distinct pods, which is why it passed while
this fails.

**Where to look:** `src/distributed/raft_consensus.zig` (RequestVote send/recv,
term advance, vote tally), `src/distributed/cluster.zig` (`sendToNode`
`findNodeEndpoint`, the tick/election loop). Worth checking whether RequestVote
RPCs are actually delivered+counted cross-pod (cluster-token frame auth, the
`0xAAAA…` uninit `node_id` seen in `Node detected as failed` logs) vs. silently
dropped.

**Note on the insecure path:** `GEODE_CLUSTER_INSECURE=1` is documented as
refused in release builds, but the published 0.6.14 image accepted it here
(handshake bypassed). Either the gate isn't effective in this build or the path
differs from `cluster_auth.isInsecureModeAllowed()` expectations — worth a look.

## TLS trust (for when Bug B is fixed) — k8s cert requirements

The cluster QUIC listener auto-generates a **per-node self-signed** cert
(`cluster.zig:504`, `cert_gen.ensureCertificatesAtPath`), so the default
(verified) path `HandshakeError`s because peers share no CA. The secure path
needs `GEODE_CLUSTER_CA_CERT` (`cluster.zig:1974`, `raft_consensus.zig:874`)
pointing at a CA that signed all members, with the leaf SANs covering the
headless pod DNS names. On k8s that means an **internal cert-manager CA** (public
CAs can't sign `*.svc.cluster.local`), and clients must then trust that CA. This
is the "document the required server cert SANs + CA env for Kubernetes" item from
GAP_ANALYSIS line 66 — still unmet.

## Deployment impact

geode-argo-arda now ships **single-node** for qa/prod (geode's recommended
production mode); the 3-node wiring (with the FQDN fix) is a disabled kustomize
component, re-enabled when Bug B is fixed. Full write-up:
`geode-argo-arda/docs/GEODE-CLUSTER-BUGS.md`.
