| GAP-0895 | Medium | Observability / stall watchdog | **Open — found 2026-06-16 during the same bulk seed.** Throughout a healthy ingest the server logs, at `error` level every ~5 s: `per-stream proto_reader stall: stream_id=0 peer=127.0.0.1 idle_ms=<N, growing> (this stream wedged while others may still be progressing; restart pod or wait for client retry)`. The flagged `stream_id=0` is the idle control stream of a normally-multiplexed connection (bulk mutations flow on sibling streams); the reported `idle_ms` was ~2.17M and still climbing on a connection only minutes old — i.e. measured from a boot/zero baseline, not last-activity, despite the watchdog's own stated intent that 0/just-started must read as not-stalled (`src/server/buffered_proto_reader_metrics.zig:47`, `src/server/proto_reader_registry.zig:241`). The message itself concedes "others may still be progressing" yet emits at `error` recommending "restart pod" — a false positive that would trip alerting/healthchecks and wrongly suggest a restart during a normal long-running ingest. | In the stall watchdog (`src/server/proto_reader_registry.zig` + `buffered_proto_reader_metrics.zig`): gate the per-stream stall error on CONNECTION-level liveness (suppress when sibling streams on the same connection are making progress), compute `idle_ms` from a real last-activity timestamp (guarding the uninitialized/boot baseline so an idle-since-open stream is not reported as multi-thousand-second stalled), and demote an intentionally-idle control stream below `error`. Test: idle control stream + actively-progressing sibling stream ⇒ no stall error emitted. |
