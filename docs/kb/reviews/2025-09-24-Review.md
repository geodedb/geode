# Geode Project Code Review

## Project Overview

**Geode** is an in-development graph database aiming for full **ISO GQL** (Graph Query Language) compliance. It is implemented in Zig and aspires to provide a distributed, ACID-compliant graph database with SQL-like query capabilities. At present, however, the project is far from feature-complete – only about _30–35%_ of planned functionality is working, according to the project’s own evidence-based analysis[\[1\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L35-L43)[\[2\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L45-L53). Earlier documentation that claimed ~95% completion has been corrected by an internal “canary” verification system, which revealed the true implementation status and forced unimplemented features to be marked as such[\[3\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L95-L98). The **canary system** uses annotated tokens in code and tests to ensure documentation matches reality[\[4\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L59-L67)[\[5\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L79-L87), an approach that has improved honesty in reporting progress. In summary, Geode currently provides a basic foundation (parser, query engine core, transactions, etc.) but lacks many advanced features and still has significant gaps to close before it meets its full product ambitions.

## Architecture and Code Quality

Geode’s codebase is structured into clear modules for different concerns, demonstrating generally strong engineering practices. Key components include a **query parser/lexer** (handling GQL syntax), an **execution engine** for evaluating queries, a **storage layer** (with in-memory and disk-backed page storage and Write-Ahead Logging), a **transaction subsystem** (MVCC for snapshot isolation), a **CDC (Change Data Capture) engine**, and placeholders for **distributed operation**, **graph algorithms**, and **security features**. The project is implemented in **Zig**, which means manual memory management; however, the code is careful about allocating and freeing structures (for example, graph algorithms allocate and free memory for working data structures) and is accompanied by extensive tests that likely catch memory errors. Code style is generally **clean and well-documented** – most source files contain explanatory comments and labeled CANARY tokens linking code to requirements. The inclusion of **100+ unit tests and 85 performance benchmarks** (covering core operations, transactions, graph algorithms, etc.) indicates a strong focus on verification[\[6\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/ACTUAL_STATUS.md#L6-L14)[\[7\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/ACTUAL_STATUS.md#L48-L56). These tests enforce deterministic behavior and performance ceilings (using variance benchmarks) to catch regressions. The canary tagging system further ensures that no feature is claimed without a corresponding test or benchmark proving it[\[8\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L74-L82)[\[9\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L89-L93). This evidence-driven approach has yielded positive outcomes: for instance, **no stale features** remain (all code is updated within the last ~60 days), and every tracked feature has at least one test or benchmark (0% of features are pure stubs)[\[6\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/ACTUAL_STATUS.md#L6-L14). In short, the code quality itself is high – **modular, well-commented, and thoroughly tested** – especially given the project’s early stage. The **engineering diligence** (test coverage, performance monitoring, and documentation sync) is a standout strength[\[10\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L233-L240).

That said, the codebase is not without issues. There are a few minor technical quirks: for example, some graph algorithm implementations ignore potential error returns when inserting into maps (risking silent failures), and a number of source files (e.g. old parser.zig and lexer.zig in the root) are essentially empty or superseded by newer modules under src/gql/ – these leftover stubs could be cleaned up to avoid confusion. The heavy use of conditional compile-time flags (e.g. feature_cluster, feature_recursive, etc. in the build) to include experimental skeletons means parts of the code are compiled in/out depending on build options[\[11\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/build.zig#L22-L30). While this is understandable for managing incomplete features, it adds complexity and potential integration debt (ensuring that when those features are finished, the scattered flag conditions won’t introduce bugs). **Concurrency** is another area of concern: the project has limited testing of multi-threaded behavior[\[12\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L170-L173) and primarily runs in a single-process, single-node context at the moment. There is no evidence yet of multi-core parallel query execution or rigorous thread safety beyond basic locks for an internal queue structure. This means that as the system scales up to multiple concurrent transactions or heavier workloads, there could be latent synchronization issues or performance bottlenecks that haven’t been revealed in the current test suite. Overall, these flaws are relatively minor and expected in an early-stage project – the foundational code quality is solid, and the main shortcomings lie in **incomplete implementations** rather than poor coding practices.

## Implemented Functionality (What Works)

Despite its incomplete status, Geode does have a core set of features implemented and working correctly (as verified by tests). The **query engine** supports fundamental **SQL-like query constructs** such as basic RETURN projections, ORDER BY sorting, and GROUP BY aggregations[\[13\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L37-L43). Simple retrieval queries can be executed, and the system can enforce basic query semantics (for example, ensuring that an ORDER BY is present when using OFFSET/LIMIT as per ISO rules). **Set operations** are implemented: queries can perform UNION, INTERSECT, and EXCEPT (each with ALL or DISTINCT variants) on result sets, which is a notable capability verified by multiple tests[\[13\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L37-L43). The **transaction subsystem** exists and provides **MVCC (Multi-Version Concurrency Control)** for snapshot isolation. You can begin transactions, perform operations, and commit them, with the engine maintaining multiple versions of data for consistency[\[14\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L37-L40). The core transaction logic (commit, and basics of SSI – Serializable Snapshot Isolation) is tested; phantom reads are partially addressed via a range-tracking mechanism in the code (to eventually prevent phantoms in serializable mode)[\[15\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L75-L83)[\[16\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L79-L87).

Geode also includes a **Change Data Capture (CDC) engine** that works at least in a single-node context. The CDC component captures write-ahead log events and can stream changes internally; its “core engine” is implemented and covered by over 50 test/benchmark variations[\[17\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L60-L69). For example, tests verify that the CDC stream maintains correct event ordering, handles malformed data gracefully, supports **resume tokens** for resuming streaming from a certain point, and applies backpressure strategies[\[18\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L62-L70). (Note: what’s missing is integration with external sinks – see “Missing Features” below – but the internal mechanics are solid.) The **schema management** features are surprisingly fleshed out: Geode enforces **schema constraints** like CHECK constraints, unique constraints, and basic pattern (regex) constraints on data[\[19\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L50-L58). The presence of these features means the engine can validate data against schema rules, ensuring things like uniqueness or format pattern matching, with tests confirming these behaviors and even benchmarks measuring any performance impact of constraint checks. Another area that is working is the **binary wire protocol** that Geode uses for client-server communication. The project implements a custom binary protocol (with handshake frames, query execution frames, etc.), and this protocol layer is fully tested and benchmarked[\[20\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/ACTUAL_STATUS.md#L19-L27)[\[21\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/ACTUAL_STATUS.md#L22-L25). For instance, the **HELLO handshake** exchange and basic RUN_GQL query messages are handled properly, and even malformed frame input is detected and triggers appropriate errors (there are tests for decoding invalid frames)[\[22\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L31-L39). The existence of a **REPL CLI** (geodec) and a server daemon (geoded) as described in the docs shows that one can run a Geode server and connect a client to it, executing queries through this binary protocol[\[23\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/USAGE.md#L9-L18)[\[24\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/USAGE.md#L22-L28). In summary, the “working” 30-35% of Geode includes: single-node query processing (for a subset of GQL), core data storage with logging, transactional commits, internal CDC streaming, schema enforcement, and the networking layer needed for a client to talk to the server (albeit only in a rudimentary manner).

It’s also worth noting that the project has implemented a variety of **graph algorithm routines** in code, even if they are not yet exposed as user-facing features. The codebase includes functions for algorithms like **breadth-first search (BFS)**, **depth-first search**, **shortest path (Dijkstra and A\*)**, **spanning tree algorithms (Kruskal, Prim)**, and centrality measures such as **PageRank** and **closeness/eigenvector centrality**. For example, there is a fully coded and tested PageRank implementation using power iteration[\[25\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/graph/centrality_pagerank.zig#L4-L12)[\[26\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/graph/centrality_pagerank.zig#L89-L98). The PageRank function builds its own internal graph representation, iterates until convergence, and returns a list of nodes with their rank scores[\[27\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/graph/centrality_pagerank.zig#L30-L39)[\[28\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/graph/centrality_pagerank.zig#L91-L100). Similarly, other graph algorithms (shortest path, flow algorithms like Edmonds-Karp, etc.) have corresponding Zig modules. Each of these algorithms has associated CANARY markers and tests/benchmarks – meaning the team has at least unit-tested the algorithm logic on synthetic data[\[7\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/ACTUAL_STATUS.md#L48-L56)[\[29\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/ACTUAL_STATUS.md#L50-L58). This is an impressive amount of algorithmic groundwork laid in the code. However, it’s important to emphasize that **these algorithms are not yet integrated into the query engine or user queries** – one cannot, for example, run a GQL query to “compute PageRank on the graph” at the moment. They exist as a library of functions and performance tests within the codebase (perhaps in anticipation of a future “Graph Data Science” component), but from a product perspective they are inactive. We mention them here as part of what’s implemented because they demonstrate technical progress and competency in graph algorithm implementations, even if the end user can’t benefit from them until further integration is done.

## Missing and Incomplete Features (Gaps)

Far more noteworthy are the features that **Geode lacks or has only partially implemented**. The project’s documentation frankly lists many major capabilities as “0% implemented” or present only as stubs[\[2\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L45-L53). Here we detail these gaps:

- **Distributed Cluster / Sharding:** Geode is not distributed in any meaningful sense yet. There is **no multi-node cluster support** – no sharding or replication of data across nodes[\[30\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L47-L51). A Raft consensus algorithm has been partially coded (for example, the code defines Raft log structures and can simulate leader election in memory), but actual networking and multi-node coordination are missing. The current Raft implementation works only with a **mock transport** via callback (no real message-passing between servers) and it lacks critical features like membership changes and snapshotting[\[31\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L190-L198). In short, while some core logic for Raft exists and passes local tests (leader election timing, log append consistency under simulated conditions)[\[32\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/distributed/raft.zig#L1-L10)[\[33\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/distributed/raft.zig#L94-L102), Geode cannot form a distributed cluster or provide high availability at this time. The **“Distributed” feature is effectively ~15% done** – just enough for a single-node with a stubbed consensus mechanism[\[34\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L176-L184).
- **GPU Acceleration:** The project advertises GPU acceleration (“10-100x faster” in older materials), but this is completely **unimplemented**. The code includes a module (gpu/flagger.zig) that simply flags every possible GPU-accelerated feature as “unsupported”[\[35\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/gpu/flagger.zig#L18-L26). There are no GPU computing kernels (no CUDA/OpenCL integration) at all[\[30\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L47-L51)[\[36\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L192-L200). In fact, the presence of a test named TestCANARY_REQ_GQL_051_GPUFlaggerUnsupported confirms that the only thing the GPU feature does is explicitly report that GPU support isn’t there[\[37\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/gpu/flagger.zig#L39-L47). Thus, any claim of GPU-accelerated query execution or graph processing is purely theoretical at this point – performance-critical operations run on CPU only, and likely single-threaded CPU at that.
- **Machine Learning & Advanced Analytics:** Similarly, any **machine learning algorithms or advanced graph analytics** (beyond the basic graph algorithms library mentioned earlier) are not implemented. The documentation notes 0% progress on “ML algorithms”[\[38\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L48-L51). Features that might fall under this category – such as graph neural network computations, community detection algorithms, or integration with ML frameworks – are entirely absent. Even within graph analytics, while the code has centrality measures and flows, higher-level “Graph Data Science” capabilities (like algorithms for clustering or predictive modeling on graph data) are not present. Essentially, **no ML or graph mining functionality is integrated or exposed**, so Geode cannot yet perform tasks like graph predictions, similarity searches, or algorithmic graph analyses as a user-facing feature[\[39\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L186-L194). This is an acknowledged gap.
- **Query Language Features (Graph GQL specifics):** Perhaps the most critical gap is that **graph pattern querying is not functional**. Geode’s query parser can recognize the GQL MATCH syntax for graph patterns, but it does not execute them[\[40\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L10-L18)[\[41\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L62-L69). The current engine can only handle the more SQL-like parts of GQL (returns, projections, set ops, basic filtering on tabular data). Core graph query capabilities – such as traversing relationships in the database using pattern matching – are **missing**. According to the conformance profile, the system _“rejects programs with proper ISO diagnostics but cannot execute graph patterns.”_[\[42\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L6-L13) In practical terms, this means if you write a query like MATCH (n)-\[r\]->(m) RETURN m, Geode will parse it (or possibly error with a “feature not supported” message) but has no runtime execution for it. The **current limitations** list is explicit: **no support for MATCH patterns, node/edge property access, label filtering, or OPTIONAL matches**[\[43\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L63-L71). Even _variable-length path queries_ (the hallmark of graph querying, e.g. MATCH p=(a)-\[\*..3\]->(b)) are not executed, despite some internal pathfinding capabilities existing in code[\[44\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L63-L70). Additionally, **graph data manipulation** is absent – there is no CREATE or DELETE of nodes/edges via queries, and no MERGE or other update clauses in GQL[\[45\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L65-L71). Essentially, Geode currently behaves more like a relational engine with a graph query veneer that isn’t hooked up: you can do returns, filtering on basic data types, grouping, etc., but you **cannot store a graph and then query the connections in that graph** using GQL patterns. This is a fundamental omission for a graph database product. The only way to add data is programmatically (e.g. via an internal API or by hardcoding data in a test); user-level DML (Data Manipulation Language) for graphs doesn’t exist yet. Until pattern matching and graph traversal queries work, Geode cannot claim to support “graph queries” in the typical sense – a huge gap relative to its goals.
- **Query Optimizer:** Geode lacks a sophisticated query optimizer. There is no **cost-based optimization** of query plans[\[46\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L49-L52). The planner likely executes queries in a straightforward way (perhaps using a rule-based or fixed strategy) without considering different join orders, index usage (since indexes are minimal), or other performance tuning choices. Documentation confirms that while some groundwork for a cost model has been laid (there are instrumentation hooks and some “plan cost model factors” being tracked), there is **no cost-based plan selection implemented**[\[47\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L14-L22)[\[48\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L171-L179). For example, the project’s next-step planning mentions adding a selectivity estimator and adaptive feedback loops, but these are still to-do or experimental[\[49\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L16-L24). The absence of a cost-based optimizer means that as queries get complex, the engine might choose suboptimal execution plans or even be unable to execute certain complex graph pattern queries efficiently (when those patterns are eventually enabled). This gap will impact performance and scalability until addressed.
- **Indexing and Search:** **Indexes** are only minimally present. The storage engine supports basic primary key indexing for the graph’s internal storage, but higher-level indexes (such as an **inverted index for full-text search** or property indexes for accelerating value-based lookups) are not implemented[\[50\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L52-L55). The docs specifically call out **“Full-text search – Not implemented”**[**\[50\]**](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L52-L55), indicating that any queries requiring text search or string indexing would be unsupported. Likewise, if you wanted to look up all nodes with a certain property value, there’s no secondary index to assist – the engine would have to scan. The **GAP_ANALYSIS** hints that features like an **inverted index** and **materialized views** are planned but currently absent[\[51\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L30-L39). **Materialized views** (precomputed query results that stay updated) are explicitly said to be “all TODOs”[\[52\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L50-L53), so nothing of that sort exists. The **lack of indexing and materialized views** means that query performance on large data sets is a concern – without these, as data grows, queries will slow linearly or worse.
- **External Integrations (CDC Sinks, etc.):** While the internal CDC engine works, **integration with external systems** (like sending changelog events to **Kafka or Kinesis**) is not done. The “CDC core engine” was built with the idea of connecting to such streaming sinks, but currently “no Kafka/Kinesis” support is available[\[53\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L39-L41). The change feed can only be consumed internally or via the Geode client if one were to read it, but you cannot yet configure Geode to publish its CDC events into an external pipeline for broader data ecosystem integration. This will be an important feature for a production system (to hook the DB into downstream consumers or audit logs), and its absence is noted.
- **Security and Access Control:** **Transparent Data Encryption (TDE)** and fine-grained access control are only stubbed out. There’s mention of TDE in the code (e.g. a tde_hierarchy.zig file and a CANARY test for key rotation) but essentially **only a single test exists for TDE key rotation**, implying the feature is not fleshed out[\[54\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L114-L121). For access control, features like **row-level security (RLS)** or **attribute-based access control (ABAC)** have build flags but no concrete implementation yet[\[55\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/build.zig#L24-L27). There is no evidence of a permission model, user roles, or anything beyond perhaps a placeholder. In effect, all security beyond basic connectivity (e.g., using TLS in the transport) is a to-do. On a related note, **multi-tenant or multi-graph support** is minimal – the docs say “Multi-graph – Basic structures only”[\[56\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L53-L56), meaning the system may have the notion of multiple graph namespaces in its metadata, but isolation and full support for operating several graphs separately is not complete. A user cannot yet spin up multiple named graphs with distinct data and enforce isolation between them in any robust way.
- **High-Availability & Fault Tolerance:** Because clustering isn’t ready, **high-availability** features (replication, failover) are nonexistent. Also, **backup/restore** was only recently addressed in development (the backlog indicates that basic backup/restore primitives were implemented[\[57\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L18-L26)). Prior to that, recovering from a node failure likely relied solely on the WAL (which does cover crash recovery on a single node). Now a “full and incremental backup” is said to be done in a recent slice[\[58\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L18-L23), but it’s new and would need testing in practice. **Online or streaming backups, point-in-time recovery**, etc., are not mentioned, so we assume those are not yet in scope.
- **Performance and Parallelism:** As hinted earlier, Geode has not yet tackled **parallel query execution** or significant **performance optimization** beyond micro-benchmarks. All query processing is likely single-threaded (one query uses one thread of one server). There’s no mention of vectorized execution or pipelined parallelism. Without GPU or multi-threading, complex analytical queries on large graphs could be very slow. Additionally, certain components are still in a basic form – e.g. the **WAL (Write-Ahead Log) and storage engine**, while functional, may not include advanced optimizations like **ARIES-style physiological logging** or fine-grained locking/latching for pages[\[59\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L101-L110). The documentation notes that ARIES optimizations and refined page management are “not yet evidenced” (i.e., not implemented)[\[60\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L104-L112). This means that the storage/recovery performance might not be up to the level required for a production database; recovery is correct (there are tests for WAL recovery and even corrupt page handling) but possibly slower or less concurrent than ideal.

In summary, Geode is **missing critical features across the board** for a graph DB product: no distributed clustering, no true graph pattern querying, no query optimizer, no index/FTS, no GPU/accelerators, no advanced analytics or ML integration, incomplete transaction isolation, minimal security, and limited tooling for management. The team is aware of these and has enumerated them as “critical gaps” with specific requirement IDs for future work[\[31\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L190-L198). It’s clear that a lot of functionality remains **unimplemented or only partially realized** in the current codebase.

## Technical Issues and Flaws in Implementation

Beyond the absence of features, there are some **design and implementation issues** that deserve mention:

- **Integration of Graph Algorithms:** As noted, there’s a disconnect between the implemented **graph algorithms library** and the query engine. This indicates a possible architectural challenge: the system has code to do things like BFS or PageRank, but currently no mechanism to feed the database’s actual graph data into those algorithms in response to a user query. Bridging this gap will require careful design – e.g. deciding how a GQL query invokes a graph algorithm and how results (like a centrality ranking) are returned or integrated into query results. The current architecture doesn’t show signs of this integration yet, which is a flaw in terms of product completeness. Until it’s solved, those algorithms (while well-written) remain isolated. On the flip side, having them implemented now is beneficial for future integration, but an external observer might see “PageRank code present” and assume the feature exists when it actually doesn’t in the user-facing sense. This can be seen as an **architectural inconsistency** – implementing backend logic far ahead of the frontend capabilities.
- **Flagging and Stubbing Strategy:** The project uses **feature flags to include/exclude experimental code** (for clustering, recursive queries, RLS, etc.)[\[11\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/build.zig#L22-L30). While this is a common approach, it means that a lot of code exists in a half-finished state protected by if (enabled) { ... } conditions. For example, the **recursive query support** (common table expressions or recursive MATCH patterns) has a flag, and some parts of it (like partial parser recognition and a fixpoint iterator) were recently added under that flag[\[61\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L53-L61). This strategy can lead to complexity: ensuring that enabling those flags doesn’t break other parts is tricky, and it can be hard for new contributors to understand which code is active. It’s a minor flaw that can be managed by good CI (and indeed, their governance checks ensure no stale or forgotten stubs remain undetected[\[62\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L34-L42)[\[63\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L48-L56)), but the approach could become unwieldy as more features are in-flight. The positive side is that they run tests with these flags on (the governance-check and canary verification make sure even the “disabled” features are at least syntactically and semantically consistent)[\[62\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L34-L42). Still, from a design perspective, so many **partial implementations living behind flags** could complicate the codebase.
- **Query Engine Limitations:** The lack of a cost-based optimizer and limited indexing were mentioned – these are not just missing features but potentially **flaws in correctness/performance** for complex queries. For instance, without a cost-based optimizer, the planner might not choose the correct join order, which could lead to extremely slow queries or even inability to execute certain multi-hop queries within reasonable time. Additionally, **no support for query** explain plans **or profiling** (aside from a mention of a PROFILE extension in docs[\[64\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L48-L55)) means developers or DBAs cannot easily diagnose slow queries. These limitations could be considered _flaws in product-level correctness_, in the sense that the database might accept a complex query but perform so poorly that it’s unusable. Right now, given the limited scope of supported queries, this isn’t a pressing issue, but as more features come online, the absence of optimization could manifest as a serious shortcoming.
- **Data Loading and Storage:** There is no clear facility for bulk loading data or even a structured **data import/export** mechanism described. Typically, a database might have tools for CSV import or a bulk ingest API, but Geode being pre-release, one currently would have to either programmatically construct the graph (using some builder API as seen in tests) or hardcode data. This is an omission that isn’t explicitly listed in docs (since it’s more a tooling concern), but it is a practical flaw – without data ingestion tools, trying out the DB on any non-trivial dataset would be cumbersome. The storage engine itself, while implementing WAL, **compaction**, and **recycling of log segments** (those features are actually in place and benchmarked[\[65\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L101-L109)), might not yet handle large data sizes gracefully. For example, fine-grained locking in the storage engine is not mentioned – this could impact concurrent transaction throughput. And while the WAL can recover from crashes (there’s a test for recovery and even for handling corrupted pages[\[66\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L103-L111)), the engine does not yet implement **point-in-time recovery** or **incremental backups** aside from the full backup feature recently added. These are more missing features than flaws, but they reflect the incomplete nature of the storage subsystem for enterprise use.
- **Concurrency and Scaling:** As pointed out, Geode currently runs essentially on one node and (likely) one thread per query. The design does include an internal **thread-safe queue** abstraction (SignaledQueue) and some multi-producer/multi-consumer variants of it, which shows the authors are thinking about thread coordination[\[67\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L60-L69). However, there’s no evidence that the core query processing is parallelized. All transactions are serially executed in one engine instance; there’s no transaction coordinator for distributed transactions (since no cluster). The **lack of contention tests** beyond one or two scenarios (they note limited lock stress tests[\[68\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L171-L173)) means we don’t yet know how the system behaves under concurrent heavy write load or many simultaneous queries. Potential issues like deadlocks in the transaction manager or stalls in the scheduler might exist but haven’t been probed. The team will need to create more rigorous **concurrency and stress tests** as they move towards a multi-user system.
- **Documentation vs Reality Drift (Historical):** One could consider the previous **mismatch between documentation and implementation** a process flaw that has been largely addressed by the canary system. In the past, the project marketed itself as nearly complete when in fact much was not done (they admitted and fixed this, archiving old aspirational docs and generating reality-check reports)[\[3\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L95-L98). Now, while this isn’t a code flaw per se, it’s a cautionary point: any **remaining tiny discrepancies between docs and code** could confuse contributors or users. Fortunately, the automated checks (ensuring every feature in docs has a CANARY test in code) minimize this risk. This rigorous approach could serve as a model for other projects, but it also adds overhead – developers must add tokens, keep gap analysis docs updated, etc., which could slow development velocity. So far it appears manageable and beneficial, but it’s something to watch in terms of maintainability.

In conclusion on flaws: none of the code-level issues are showstoppers or indicative of poor design; rather, the project’s **architecture seems well-conceived** but just **unfinished**. Most “flaws” are direct consequences of features being only partially realized. As those features get completed (distributed execution, query optimization, etc.), many of these concerns should be resolved. The key is that the team appears to be systematically identifying and addressing gaps – albeit focusing first on core correctness and evidence of each feature, then moving to the next. This methodical progression bodes well for eventually ironing out the current limitations.

## Future Development: Recommendations and Next Steps

To evolve Geode into a complete, competitive graph database, a number of major steps remain. Many of these are already known to the team (and appear in the “Critical Gaps” or backlog documentation), but we will enumerate them with some additional insight and priority:

- **Complete the Distributed Architecture:** Implement the remaining pieces of clustering. This means finishing the **Raft consensus** implementation – adding robust leader election (with network message handling and timeout variance covered), implementing log **snapshotting** (to truncate the Raft log and manage state size), and handling membership changes (adding/removing nodes) for a dynamic cluster[\[36\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L192-L200). Beyond Raft, true distribution will require **data partitioning (sharding)** across nodes and a **cluster coordinator** to route queries to the correct shard. None of that exists yet, so it’s a top priority for achieving horizontal scalability. The groundwork (Raft append/commit logic) is there, but networking and sharding are not. A realistic next step is to incorporate a network messaging layer for Raft (perhaps using the existing QUIC protocol work for node-to-node comms) and to start with simple replication (e.g., a primary-follower setup using Raft). **Sharding** (partitioning the graph by some key or by vertex subsets) can be approached once basic replication works. Achieving a functional multi-node cluster will vastly increase Geode’s viability.
- **Graph Query Execution (MATCH patterns and traversals):** This is arguably _the_ defining feature of a graph database. The engine must support executing **graph pattern queries** specified by MATCH clauses. To do this, the team needs to integrate their traversal logic with the query planner/executor. They should implement algorithms like **subgraph isomorphism matching** or at least basic join-based expansions to find paths between nodes according to the pattern. The internal path-finding routines (BFS/DFS, etc.) can be leveraged here. Key tasks include supporting **variable-length path matches** (e.g., the \* quantifier in GQL patterns) by using either iterative deepening or leveraging existing DFS/BFS code[\[69\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L2-L10)[\[70\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L13-L21), implementing **label and property filters** during traversal (so the pattern (n:Person)-\[KNOWS\]->(m:Person { age: 30 }) can be enforced), and handling **OPTIONAL MATCH** (which is akin to an outer join in relational terms). The parser already recognizes these constructs[\[71\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L62-L70); the next step is to implement the **planner rules and executor support** for them. This will likely require introducing new plan operators or execution primitives specifically for graph traversal and expanding relationships. Given the complexity, the team might start with simpler cases (e.g., single-hop relationships and bounded-depth traversals) and then generalize. Enabling **property access on nodes/edges** in queries is also important (right now, something like RETURN n.name isn’t working[\[72\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/gql/GQL_CONFORMANCE_PROFILE.md#L63-L67)). This means the engine needs to store and retrieve node properties in its storage layer and expose them via the query environment. In summary, **making MATCH work** will transform Geode from a SQL-like engine into a true graph database, so it should be a top priority in upcoming development.
- **Implement a Cost-Based Query Optimizer:** As more query features come online (especially graph pattern queries which can be highly complex), a cost-based optimizer is essential for performance and correctness. The team should develop a **cost model** for graph operations – e.g., estimates of the number of neighbors a node has (degree distribution), estimates for filter selectivity on properties, etc. Using these, they can then implement **plan enumeration**: for example, in a multi-hop pattern MATCH (a)-->(b)-->(c), the optimizer could choose an order to expand relationships (maybe start from the smallest degree node to reduce intermediate results). The groundwork is partially laid (they have started a selectivity estimator and mention “plan cost model factors” in the backlog[\[73\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L20-L25)). Next steps include writing a **planner module** that can produce alternate query plans and score them using the cost model, then pick the lowest-cost plan. This will also involve creating **statistics** collection (perhaps as part of the storage engine or via an ANALYZE command) to inform the cost estimates. In addition, adding support for **query hints** or an EXPLAIN facility would be useful so developers can see what plan the optimizer chooses. The team’s own documentation lists cost-based optimization as a known gap[\[74\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L196-L199), so addressing it will be crucial for the 1.0 product milestone.
- **Add Indexes and Full-Text Search:** To improve query performance and capabilities, Geode needs support for **secondary indexes**. This could start with simple **property indexes** (e.g., a B-tree or hash index on a specified node property or table column, to speed up lookups by value). The engine and query planner would then need to recognize when an index can be used for a given filter (for example, if a query has WHERE n.age = 30, an index on the age property of nodes should be utilized). In parallel, implementing **full-text search** functionality would open up new use cases – this likely means integrating an inverted index structure for string properties, and perhaps using existing libraries or algorithms for text indexing. The documentation explicitly flags full-text search as missing[\[50\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L52-L55), so it’s something to consider for the roadmap. Even a basic full-text index on certain node properties with support for simple CONTAINS or MATCHES queries would be beneficial. Both indexing and FTS will significantly enhance Geode’s query power and performance, especially as data volumes grow.
- **External Integrations & Ecosystem:** Beyond the core database features, Geode should consider building out its ecosystem integration: for instance, finalizing the **CDC connectors** for systems like **Kafka**. This would involve writing producers that can take the stream of change events and publish them to external topics/streams in the appropriate format (Avro/JSON, etc.). Similarly, adding support for **graph import/export** (e.g., supporting the popular CSV import format or Cypher’s LOAD CSV, or exporting to formats like GraphML or JSON) would greatly improve usability. Another integration point is to possibly support **Cypher or Gremlin** query languages in addition to GQL. Since ISO GQL is still new, many users know Cypher (from Neo4j) – having a compatibility layer or translator (even if partial) could broaden adoption. This is not mentioned in existing docs and might be beyond current plans, but it’s a strategic consideration not to be overlooked.
- **Performance Engineering (GPU, Parallelism):** To meet the demands of large-scale graph analytics, revisiting the idea of **GPU acceleration** and **parallel processing** is important. Once the baseline functionality is there, the team could implement selective GPU kernels for things like graph algorithms (e.g., parallel BFS or PageRank on GPU) and use the GPUFlagger concept to detect and use GPU capabilities where available. The current approach simply disables GPU usage[\[35\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/src/gpu/flagger.zig#L18-L26), but with proper design, Geode could offload certain computations to GPU if it detects, for example, a very large graph algorithm job and a capable GPU in the system. Similarly, introducing **multi-threading** for query execution on CPU – for instance, evaluating parts of a query plan in parallel (especially for analytical queries that touch lots of data) – could vastly improve throughput. The SignaledQueue structures present in code suggest the team has the building blocks for thread coordination[\[75\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L60-L68); they could start by parallelizing simple operations (like applying a filter condition across many elements in parallel, or exploring multiple branches of a graph search in parallel threads). These enhancements are more long-term, but they align with the project’s performance goals (and the early marketing of “10-100x faster with GPU” once actual acceleration is in place).
- **Completing Transaction Features (SSI and Beyond):** The transaction subsystem should be extended to full **Serializable isolation (SSI)**. Currently, snapshot isolation with a phantom prevention mechanism (range locking via the RangeTracker) is partially implemented[\[15\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L75-L83). The team should finish the detection of phantoms and write conflicts to ensure true serializability when configured. This might involve implementing index-range locks or predicate locks so that a transaction that reads a range of values can block another that inserts a value in that range (the essence of phantom prevention). Additionally, support for **rollback and savepoints** could be added (not mentioned yet, likely not implemented). Ensuring that **deadlock detection** or avoidance is in place (if they use locking for SSI) will also be important as concurrency increases. Also, **multi-graph transactions** (if multiple graphs can be updated in one transaction) and distributed transactions (if sharding is implemented) are future concerns – but those build upon first getting single-node SSI solid.
- **Security and Authentication:** The project will eventually need at least basic authentication (user accounts, perhaps roles) and encryption at rest (to fulfill the promise of TDE). Finishing the **TDE** implementation – i.e., actually encrypting data files with a key hierarchy and allowing key rotation – would be a significant feature for enterprise use. Similarly, implementing **access controls** (even just read-only vs read-write users, or simple label-based access restrictions) would be valuable. Given RLS/ABAC are flagged behind a feature switch, fleshing those out (for example, row-level security policies that filter which nodes/edges a given user can see) would set Geode apart in terms of fine-grained security. In the near term, even a simpler **permission model** (admin vs regular users, etc.) and ensuring all client-server traffic can be done over TLS (the QUIC support implies TLS 1.3 for transport is already in the works[\[76\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/USAGE.md#L3-L11)) are prudent steps.
- **Polish and Tooling:** Rounding out the product will require some polish: improving the **CLI experience** (the REPL is basic, but adding things like command history – which it appears they just added, and helpful commands like :schema or :help as they have started implementing[\[61\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L53-L61) – will make it more user-friendly), providing **better error messages** for unsupported features (so that instead of failing mysteriously, the user is told “graph pattern matching not implemented” which is likely done via diagnostics already), and writing thorough **user documentation and examples** once more features work. The documentation should be continuously updated (their governance requires docs be refreshed within 24h of changes[\[77\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/NEXT.md#L32-L40), which is good). Also, adding a suite of **end-to-end example use cases** – e.g. a small social network graph that can be loaded and queried – would help demonstrate the product to potential users and testers.

In the near future, according to the project’s own roadmap, the focus should be on those **“Critical Gaps”** that currently lack any CANARY evidence[\[31\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/IMPLEMENTATION_REALITY.md#L190-L198). In priority order: finishing Raft and distribution (#1), implementing GPU kernels (#2, though this might be lower priority in practice compared to functional gaps), graph analytics integration (#3), QUIC transport (making sure the new QUIC support is complete and stable) (#4), materialized views (#5), full-text search (#6), multi-graph (#7), and cost-based optimizer (#8). Each of these will move Geode closer to a feature-complete state. Given limited resources, a realistic plan might be: **complete distributed support and basic graph querying first**, since those are core to being a graph DB; then tackle the performance enhancements (optimizer, indexes, GPU) in parallel with secondary features like full-text and security.

## Conclusion

Geode is a promising but **significantly incomplete** graph database system. The code review shows a project that is being built with careful attention to correctness – evidenced by thorough testing and a unique documentation verification mechanism – but which still has a long way to go in terms of features and real-world readiness. The **technical implementation** so far is solid for the fundamentals: the code is well-organized, and the features that are implemented (query parsing, basic execution, MVCC, schema checks, WAL, etc.) appear to be done correctly and tested thoroughly. The use of CANARY tokens to tie requirements to code and tests gives confidence that where the project claims a feature works, it genuinely has the evidence to back it up[\[4\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L59-L67)[\[8\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L74-L82). This is a strong point in code quality and process.

However, many **flaws and gaps** exist primarily because large portions of the intended functionality are unimplemented or only skeletal. At the **product level**, Geode is neither complete nor correct yet for many use cases: you cannot truly use it as a graph database today without running into unimplemented features (like graph pattern queries or distributed scaling). Critical algorithms for graph queries (like traversal and pattern matching) are still missing in action, and advanced functionalities (distributed transactions, query optimization, security, etc.) are pending. In its current state, Geode might handle small-scale or demo scenarios (single-node, simple queries on a predefined dataset) but would **fall short of expectations** for any complex analytical workload or large graph dataset.

On the positive side, the awareness of these shortcomings is high within the project. The developers have meticulously catalogued what works and what doesn’t, using an evidence-based approach to guide development[\[2\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L45-L53). The next steps they’ve outlined address the right areas: closing the gap on core graph querying capabilities, making the system truly distributed, and improving performance via optimization and indexing. By following this roadmap – and perhaps incorporating the additional recommendations above – Geode can progress towards its ambitious goal of a full-featured, high-performance graph database. There is quite a bit of heavy lifting ahead: implementing pattern matching execution, refining the storage and transaction machinery for distribution, and ensuring all of it runs efficiently. Yet, given the **strong foundation** (in code quality and testing rigor) we see in the current code, there is a reasonable likelihood that Geode will continue to improve and eventually deliver much of its promised functionality. It’s just not there as of September 2025.

In summary, this code review finds **Geode’s implementation to date to be of high quality in terms of engineering practice**, but the project is **feature-incomplete** and exhibits various _implementation gaps_. To move forward, the team should focus on the outlined missing features and potential improvements. If they do so, addressing technical flaws along the way, Geode could evolve from its current prototype phase (roughly one-third complete[\[1\]](https://github.com/spyderorg/geode/blob/d2baefaade4799e4c5af503de0e8d816272f850b/docs/README.md#L35-L43)) to a robust graph database product in the future. The key will be maintaining the evidence-driven development discipline while accelerating the delivery of major features like distributed operation and full graph query support. Each of those milestones will significantly boost Geode’s product-level completeness and correctness.

Overall, the **code quality, testing, and documentation hygiene are commendable**, but achieving the vision of Geode will require sustained effort on the many unimplemented features identified. This review highlights those areas and encourages prioritizing the graph query execution and distribution features, as they represent the core of what users will expect from a “graph database” named after a multifaceted gemstone – many faces (features) of which are still uncut and unpolished, awaiting the next phases of development.
