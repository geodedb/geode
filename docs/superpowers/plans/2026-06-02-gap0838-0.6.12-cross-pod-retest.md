# GAP-0838 re-test on geode 0.6.12 — cross-pod Raft handshake STILL fails

> **TL;DR — Conclusive: geode 0.6.12 does NOT fix GAP-0838.** A throwaway
> 3-node cluster on the published `geodedb/geode:0.6.12` image, tested in
> BOTH the unverified-TLS and the CA-verified peer paths, reproduces the
> exact 0.6.7 failure: every node logs
> `raft transport getOrCreatePeerConnection failed error=HandshakeError`
> (18 occurrences in 300 log lines) and stays `state=candidate`/`follower`
> at `term=0` — **no leader is ever elected**. The cross-pod Raft QUIC/TLS
> peer handshake remains broken between distinct pod IPs. GAP-0838 stays
> **OPEN / Critical**. Do not deploy a multi-node geode cluster until a
> release explicitly fixes the peer handshake.

- **Date:** 2026-06-02
- **Image under test:** `geodedb/geode:0.6.12` (current published release)
- **Prior failing version:** `geodedb/geode:0.6.7` (see GAP-0838 in
  `docs/GAP_ANALYSIS.md` and `docs/superpowers/plans/2026-05-27-cluster-final-status.md`)
- **Environment:** Kubernetes (DiveLife QA, namespace `divelife-qa`, CNI
  `kube-flannel`, single node `ori` — all pods co-located, intra-node open
  networking, NetworkPolicy not enforced by the CNI).
- **Verdict:** GAP-0838 unresolved in 0.6.12. Behaviour identical to 0.6.7.

## Why this re-test

geode was upgraded 0.6.7 → 0.6.12 in DiveLife QA (single-node) to pick up
unrelated fixes. Because GAP-0838 (cross-pod Raft TLS handshake) is the sole
blocker keeping that deployment parked at `replicas: 1`, the question was
whether 0.6.12 had fixed the peer handshake and the cluster could finally be
formed. This document is the controlled answer.

## Method — isolated throwaway 3-node StatefulSet (zero production risk)

To test the cross-pod handshake **without** disturbing the production
single-node `geode-0` (which serves the live api/pds), a disposable
StatefulSet `geode-ct` was stood up alongside it and torn down afterward:

- **Image:** `geodedb/geode:0.6.12`.
- **Topology:** 3 replicas, `podManagementPolicy: Parallel`, headless
  Service `geode-ct` (`clusterIP: None`, `publishNotReadyAddresses: true`,
  UDP 3141 client + UDP 4242 raft).
- **Raft config** (identical shape to the production `a506322` attempt):
  entrypoint derives `GEODE_NODE_ID` from the pod ordinal (`geode-ct-0`→1,
  `-1`→2, `-2`→3); `--cluster-port 4242`; identical `GEODE_PEERS` =
  `geode-ct-{0,1,2}.geode-ct.divelife-qa.svc.cluster.local:4242`;
  `GEODE_CLUSTER_TOKEN` from the shared QA secret; per-pod PVC via
  `volumeClaimTemplates` (each Raft node owns its own log/state on a fresh
  volume).
- **TLS:** a dedicated cert-manager `Certificate` (`geode-ct-tls`) issued by
  the existing CA `Issuer` `geode-ca`, with SANs covering the headless
  service DNS **and each pod DNS** (`geode-ct-{0,1,2}.geode-ct…`). The
  issued secret carried `tls.crt`, `tls.key`, and `ca.crt` (verified
  present). Mounted read-only at `/certs`; `geode serve --cert /certs/tls.crt
  --key /certs/tls.key`.

All three pods reached `1/1 Ready` (the readiness probe only checks the
client QUIC port 3141 is bound — it does **not** assert Raft quorum, so
"Ready" here does not mean the cluster formed).

## Result — both TLS paths fail identically

### Path A — default / unverified peer TLS (`GEODE_CLUSTER_CA_CERT` unset)

This is the exact path the geode-test-harness exercises on loopback. On
distinct pod IPs it fails immediately:

```
WARN geode.raft raft transport getOrCreatePeerConnection failed error=HandshakeError peer=3
WARN geode.raft raft transport getOrCreatePeerConnection failed error=HandshakeError peer=2
... (repeating ~1×/sec on every node)
[raft] node 1 state=candidate term=0 iter=1400
[raft] node 1 state=candidate term=0 iter=1500
```

### Path B — CA-verified peer TLS (`GEODE_CLUSTER_CA_CERT=/certs/ca.crt`)

The leaf-cert secret includes the issuing CA (`ca.crt`), and the leaf chains
to `CN=geode-ca` (a real `isCA:true` CA, the chain GAP-0838's remediation
called for). After setting `GEODE_CLUSTER_CA_CERT=/certs/ca.crt` and
restarting all three pods, the handshake **still** fails:

```
geode-ct-0 HandshakeError count (last 300 log lines): 18
WARN geode.raft raft transport getOrCreatePeerConnection failed error=HandshakeError peer=3
WARN geode.raft raft transport getOrCreatePeerConnection failed error=HandshakeError peer=2
```

### Leader election — never happens

Across all three nodes, the only Raft states ever observed were
`state=candidate` and `state=follower`, always at `term=0`. **No node ever
reached `state=leader`; the term never advanced past 0.** Without a quorum
the cluster cannot elect a leader, replicate, commit writes, or serve
consistent reads — i.e. the multi-node feature is non-functional, exactly as
GAP-0838 documented for 0.6.7.

## Corroborating observation — no cluster-CA / peer-trust flag in 0.6.12

`geode serve --help` on the 0.6.12 image exposes only:

```
  --cert <path>          TLS certificate path (auto-generated if missing)
  --key <path>           TLS private key path (auto-generated if missing)
```

There is **no** `--cluster-ca` / peer-trust / peer-verify flag. The
CA-verified path is reachable only via the `GEODE_CLUSTER_CA_CERT`
environment variable (as in the 0.6.7 attempt), and as shown above it does
not change the outcome.

## What this rules in / out

- **Not a deployment misconfig (re-confirmed):** the cert SANs cover every
  peer's pod DNS; the leaf chains to a real CA whose `ca.crt` was provided;
  all pods are co-located intra-node with open networking; the Ready gate
  passed. The same ruled-out set as the original GAP-0838 audit holds (cert
  SANs, CA trust, connectivity/NetworkPolicy, ALPN/port).
- **Regression status:** no regression and no fix — behaviour is **identical**
  to 0.6.7. The cross-pod peer handshake has not been addressed between 0.6.7
  and 0.6.12.
- **Loopback-only validation persists:** the harness still validates the
  cluster only on `127.0.0.1`; the gap between that and a real multi-IP
  deployment is unchanged.

## Cleanup

The throwaway test was fully removed after the run — `StatefulSet/geode-ct`,
`Service/geode-ct`, `Certificate/geode-ct-tls`, `Secret/geode-ct-tls`, and
all three `data-geode-ct-{0,1,2}` PVCs deleted. Production `geode-0`
(single-node, 0.6.12) was never touched and remained healthy throughout
(api + pds `/healthz` reported `geode:ok` before and after).

## Implications / recommendation

- DiveLife QA geode **stays single-node** (`replicas: 1`). Do not re-attempt
  the 3-node cluster on 0.6.12.
- GAP-0838 remains **OPEN / Critical**. Its recommended fix and acceptance
  criteria are unchanged and now have a second data point (0.6.7 **and**
  0.6.12): the peer handshake must be fixed for distinct IPs, and a
  **non-loopback** (separate netns/containers) TLS cluster integration test
  must be added to CI so this is caught at the source instead of at
  deployment.
- A vendor-QUIC-level TLS-alert capture is still needed to distinguish the
  precise rejection cause; geode's logger surfaces only the wrapped
  `HandshakeError` even at `--log-level debug`.

## Reproduce

1. Issue a cert-manager `Certificate` from a real CA `Issuer` with SANs for
   `geode-ct-{0,1,2}.<svc>.<ns>.svc.cluster.local` (+ the headless svc DNS).
2. Apply a headless `Service` (UDP 3141 + 4242) and a 3-replica,
   `podManagementPolicy: Parallel` StatefulSet on `geodedb/geode:0.6.12` with
   the ordinal→`GEODE_NODE_ID` entrypoint, `--cluster-port 4242`, identical
   `GEODE_PEERS`, `GEODE_CLUSTER_TOKEN`, and per-pod PVCs.
3. `kubectl logs <pod>` → observe `getOrCreatePeerConnection failed
   error=HandshakeError` and perpetual `state=candidate term=0`.
4. Optionally add `GEODE_CLUSTER_CA_CERT=/certs/ca.crt` and restart →
   identical failure.

## Resolution (2026-06-02) — root cause found and fixed

> The 0.6.12 failure documented above is real, but the cause is **not** a
> deployment misconfig or a missing trust anchor. After building a hermetic,
> non-loopback, secure-mode reproduction
> (`tests/test_gap0838_cluster_tls_noloopback.zig` — a `QuicTransport` server on
> `127.0.0.2` with a real openssl CA-issued cert, driven by a `QuicClient`
> secure handshake), the true root cause was pinned:

**A client-side TLS 1.3 handshake-transcript fold-order bug in the shared
`devnw/zig/tls` library** (`tls13/context.zig` `processCrypto`). The inbound
handshake loop folds every message into the transcript *before* dispatch
except `.finished`; `.certificate_verify` was not excluded. So the client
finalized `H(…‖Certificate‖CertificateVerify)` to verify the server's
signature, while the server correctly signs `H(…‖Certificate)` (RFC 8446
§4.4.3). Result: **every secure handshake fails at `CertificateVerify` with
`error.InvalidSignature`.** `GEODE_CLUSTER_INSECURE=1` masked it by skipping the
CV check entirely — which is why loopback/harness "worked" and real
deployments (where insecure is refused in release builds) never could. Verified
TLS server-authentication had effectively never worked in this `quic`/`tls`
stack.

Why both 0.6.12 paths in this report failed:
- **Path A (no `GEODE_CLUSTER_CA_CERT`)** — no trust anchor *and* the CV
  transcript bug; would fail regardless.
- **Path B (`GEODE_CLUSTER_CA_CERT=/certs/ca.crt`)** — trust anchor + chain
  were fine (now confirmed: x509 chain validation passes), but the CV
  signature check fails on the transcript divergence. This is why a correct
  CA chain still produced `HandshakeError`.

**The fix** (one localized change): in `processCrypto`, also exclude
`.certificate_verify` from the pre-dispatch transcript fold and fold it *after*
the handler verifies it — mirroring the existing `.finished` handling and the
server's own `emitServerFlight` ordering (fold Certificate → sign CV → fold
CV). The same change fixes both client server-auth and the symmetric mTLS
client-auth path (they share the loop).

**Validation:** the new regression test passes 3/3 (both secure positive cases
now succeed on a distinct IP; the no-trust negative case still correctly
fails); the tls library's own unit tests, `test-cluster-coord-config`, and
`test-cluster-forward-to-shard` all pass.

**Deployment guidance:** the 3-node cluster is viable once geode ships a build
containing this TLS fix (the `devnw/zig/tls` change re-pinned through
`quic` → geode `build.zig.zon`), with `GEODE_CLUSTER_CA_CERT` pointed at the
cert-manager CA (`/certs/ca.crt`) and per-pod-DNS SANs as already configured.
Until that release lands, stay single-node. Full fix plan + root-cause detail:
`docs/superpowers/plans/2026-06-02-gap0838-cross-pod-tls-fix.md`.
