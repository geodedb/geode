# Integrating Signal-Based Anomaly Detection into Geode

## Geode’s Time-Series Architecture and Current Capabilities

Geode is a graph database that recently gained native time-series support, enabling unified storage and querying of graph‑linked telemetry data. Under the hood, Geode stores time‑series as columnar chunks of points with **Gorilla compression** (delta‑of‑delta timestamps and XOR value encoding) for high efficiency \[1]. Each logical series (e.g., a device’s metric) is partitioned into fixed‑size chunks (4096 points each) that are compressed to \~1.5–8 bytes/value depending on regularity \[1]. This chunked design allows fast time‑range scans by skipping chunks outside the query window and yields high write throughput by buffering points into chunks. In the graph data model, time‑series are treated as first‑class related data: for example, each `Device` node has a child `Series` node per metric, which in turn links to multiple `Chunk` nodes holding the actual time‑slices \[2]. This **“chunked series subgraph”** model preserves graph semantics (devices and sensors remain nodes) while storing bulk measurements in an efficient structure.

Geode’s query engine has been extended with time‑series functions to retrieve and aggregate these sequences. Built‑in **GQL** functions include getting the latest value, point‑at‑time lookups, downsampling (`sample_by`), interpolation, moving averages, rate of change, derivatives, and time bucketing \[3]. These functions can be used seamlessly within graph queries. For example, one can match a sensor device in the graph and retrieve the last reading of a metric in the same query, thanks to Geode’s unified graph+TS model \[4]. Internally, Geode ensures such queries remain efficient by co‑locating series data with the associated node and **pushing down temporal filters** to quickly prune irrelevant chunks \[1]. Performance benchmarks already show millisecond‑level latencies for basic operations: e.g., point‑in‑time lookups and recent window scans complete in \~200 ms even for large series, and aggregating 10,000 series in parallel over 1‑hour windows finishes in \~250 ms (95th percentile) by leveraging chunk indexes and parallel reads \[1]. Ingestion is similarly high‑throughput (on the order of millions of points per second per node) with durability via Geode’s WAL and compression reducing storage footprint by \~60% \[5]\[6].

These capabilities provide a solid foundation for building **in‑situ anomaly detection**. Geode’s time‑series extension is architecturally “opt‑in” – time‑series data behaves like attached properties in the graph, without needing an external TSDB \[7]. This unified model avoids the “sidecar” approach (where a separate time‑series store is kept in sync with the graph) and ensures no semantic drift: temporal queries in GQL return the same results as equivalent pure graph expansions \[7]. Additionally, Geode supports **streaming queries** and **change‑data‑capture (CDC)** for time‑series inserts \[8]. This means the system can continuously process incoming data (with watermarks to handle out‑of‑order timestamps) and even maintain rolling aggregations or materialized views on the fly \[9]. In summary, Geode can store high‑volume time‑series data and query it with low latency, providing the necessary primitives (fast sequential access, windowing, and streaming update hooks) to embed advanced signal‑processing and anomaly detection logic.

## Inserting Spectral Analysis into Geode’s Data Flow

To detect subtle cyber attack patterns in time‑series (network traffic, logon attempts, IoT sensor readings, etc.), we will integrate **spectral and time‑frequency transforms** into Geode’s data flow. The goal is to catch anomalies that are hard to spot in raw time‑domain signals but become evident after transformation (for example, a beaconing C2 channel that looks like sporadic noise in time may show a narrow‑band frequency spike in the Fourier spectrum \[10]). Geode’s pipeline offers several integration points for these transforms:

### On Ingestion (Real‑Time Path)

As new data points stream into Geode, we can apply signal‑processing in near‑real‑time before or just after they are written to the chunk store. One approach is to maintain a sliding window of recent data for each series and update its spectral representation incrementally. For example, every time a chunk is filled (or every fixed time interval), Geode could compute an **FFT** or **wavelet transform** on the latest window of points and immediately run anomaly detection on that transformed output. By hooking into the insert path (e.g., via Geode’s **CDC** mechanism), we can trigger analysis as data arrives \[11]. Geode’s design already envisions streaming computations using windowing – an example in the design docs shows a continuous query that computes a tumbling window aggregate on a series as new points arrive \[9]. We would implement a similar continuous anomaly detection query: for instance, a rolling **spectral residual** computation on the last _N_ points of a series, followed by an anomaly scoring function. The continuous query mechanism (materialized views) would ensure this runs automatically in the background, emitting anomalies shortly after data arrival. Leveraging the existing transaction and partitioning system, each shard (partition) can process anomalies for series it hosts in parallel, preserving the distributed throughput. **Watermark logic** can be used to decide when a window is “complete” enough to analyze, ensuring we wait for late‑arriving data up to a tolerance \[11]. By integrating at ingestion time, we aim to catch fast‑moving threats with minimal delay – the research target is a detection latency **under 200 ms** from data arrival \[12], which is feasible if computation is efficient and possibly batched per chunk.

### On‑Demand Query (Analytical Path)

In addition to continuous monitoring, Geode will support explicit anomaly detection queries on historical data. A security analyst might request: “find anomalous patterns in the last 24 hours of traffic on device X” or “compute the wavelet scalogram for sensor Y and flag outlier segments.” To enable this, we plan to introduce new GQL **user‑defined functions or procedures** for signal transforms and anomaly scoring. For example, a function `fft(series, start, end)` might return the frequency spectrum of a series over the specified interval, and a function `detect_anomalies(series, method, params, window)` could return a list of anomaly timestamps or an anomaly score time‑series. Under the hood, these would utilize Geode’s **vectorized query engine** to operate directly on compressed chunk data in memory (decompressing on the fly and performing math in C/Zig). Because Geode can perform vectorized scans and even **optional GPU offload** for large computations \[13], on‑demand spectral analysis can be quite efficient – e.g., computing an FFT on tens of thousands of points or generating a short‑time spectrogram can be done within a few milliseconds on CPU, or even faster on GPU if the data size is large. By embedding these capabilities in the query engine, analysts can leverage complex anomaly detection without exporting data. For instance, one could run a GQL query that matches certain devices and filters by an anomaly score function:

```cypher
MATCH (d:Device)-[:HAS_SERIES]->(s:Series {metric: "net_traffic"})
WHERE spectral_anomaly_score(s, last_1h) > 0.8
RETURN d;
```

The engine would compute the spectral features (e.g., via FFT or wavelet) for each series `s` over the last hour and evaluate an anomaly score (perhaps via the spectral residual or other algorithm), returning devices with high scores. This tight integration makes advanced analysis just another query, benefiting from Geode’s existing optimizations (time filter pushdowns, parallel chunk scanning, etc.). On‑demand analysis is useful for forensic investigations or periodically scheduled jobs, complementing the real‑time alerts from the ingestion path.

### Batch or External Analysis (Augmented Path)

While the preference is to handle detection natively, there may be cases where extremely advanced processing is needed that doesn’t fit well inside the DB (for example, lengthy model training or global correlation across many series). In these cases, Geode’s extensibility allows for an external pipeline to consume data and feed results back. Geode can use its **CDC feed** or client subscription APIs to stream time‑series data out to a dedicated analytics service (like Apache Flink, Spark, or a Python‑based microservice) for heavy‑duty anomaly detection. This external service could perform complex tasks (e.g., training a deep autoencoder on months of data, or running an ensemble of many algorithms from the research toolkit) and then write the detected anomalies or scores back into Geode (as new nodes or properties). However, this introduces additional latency and deployment complexity, so we consider it a fallback for off‑line analysis or prototyping. The design intent is to **minimize reliance on sidecar processing** \[14]; instead, we incorporate as much streaming logic into Geode as possible. In fact, the Geode team explicitly decided to “incorporate simple stream processing via window queries in Geode itself” rather than require an external stream processor \[14]. Therefore, our integration emphasizes in‑engine processing for real‑time needs, while allowing batch/offline workflows (using exports or CDC) for deeper analysis if needed.

By inserting spectral transformations and anomaly detection at these strategic points, Geode can detect anomalies both **continuously** (triggering alerts as soon as suspicious behavior emerges) and **on‑demand** (supporting rich forensic queries). The combination leverages Geode’s strong points – transactional ingest, fast time‑series scans, and graph context – to provide a comprehensive anomaly detection capability without leaving the database environment.

## Extending Geode with Signal‑Processing Modules

To implement the above, we need to extend Geode’s engine with modules that perform the required transforms and anomaly algorithms. We have several options for doing this natively within Geode versus using external components:

### Native Zig/C++ Implementation

Geode is written in **Zig**, which can interoperate with C/C++ libraries. We can integrate high‑performance numeric libraries (for FFT, wavelets, etc.) or implement algorithms directly in Zig for tight integration. For example, we might embed an FFT library (like **FFTW** or **KissFFT**) to compute frequency spectra of series in‑place. Given that typical window sizes for detecting cyber anomalies might be on the order of a few thousand points (for example, analyzing the last few seconds or minutes of high‑rate data), even a plain C FFT will be extremely fast on modern CPUs. **Wavelet transforms** (e.g., discrete wavelet transforms for multi‑scale analysis) could be implemented using existing C libraries or by writing a Zig routine for the specific wavelet families of interest. Other spectral methods mentioned in the research (like **Lomb–Scargle** for irregular sampling or **Hilbert–Huang** via empirical mode decomposition) are more complex; these might be initially supported via external tools or approximated with simpler methods. The plan is to start by natively supporting core transforms (**Fourier FFT**, **Short‑Time FFT**, and a few common **wavelet** bases) and see which advanced techniques are truly needed in real‑time. The research hypothesis is that many stealthy attacks will become visible with these classical transforms \[10]\[15], so covering FFT and **CWT** (continuous wavelet transform) is a priority.

On the anomaly detection side, we will implement a suite of detection algorithms that operate on the transformed features or on raw series. Simpler methods like **thresholding** a spectral feature or applying a **CUSUM** change detector can easily be coded in Zig and run per time‑step or per window \[16]. For instance, we might compute the power in a specific frequency band and raise an anomaly if it exceeds a learned threshold (indicating, say, an abnormal spike at that frequency). **Change‑point detection** (CUSUM, **EWMA** control charts) on streaming features can be done incrementally with low overhead. More advanced unsupervised detectors – like an **Isolation Forest** or **one‑class SVM** on feature vectors – are heavier, but could be integrated via a C++ ML library (for example, Intel’s oneDAL or LIBSVM). However, these may not meet real‑time latency unless the feature vector is very low‑dimensional; they might be more suitable for on‑demand analysis rather than per incoming point.

One standout method from the research is the **Spectral Residual (SR)** algorithm and its **SR‑CNN** variant. SR is attractive because it is fast and unsupervised: it takes a Fourier spectrum, logs it, filters out the general trend, and finds the “residual” that stands out; this residual can signal an anomaly even in a single series by highlighting unexpected frequency content. We can implement SR easily after computing an FFT of a window – it’s basically a few array operations (smoothing and subtraction in the log‑frequency domain). The SR‑CNN variant then feeds the residuals into a lightweight convolutional neural network to refine anomaly detection. Embedding a CNN inside the database is challenging but feasible: since SR‑CNN models reported by Ren et al. are small (and gave \~20% F1 improvement over prior state‑of‑art), we could pre‑train a CNN (perhaps using PyTorch or TensorFlow on similar data) and then export it to an efficient inference runtime. One approach is to use an **ONNX Runtime** or **TensorRT**, which are C/C++ libraries that can run neural nets quickly on CPU or GPU. Geode’s engine could link against such a runtime so that when `spectral_anomaly_score()` is called with `method="SR-CNN"`, it performs SR to get a residual sequence and then runs the CNN model in inference mode to produce an anomaly score for that window. Because the model is fixed and relatively small, inference can be under the 200 ms budget even on CPU (potentially a few milliseconds per evaluation). We will need to manage the overhead of loading models – ideally, keep the model in memory and reuse it for all series rather than reload per query.

### Scripting and WASM Extensibility

While writing everything in Zig/C provides speed, it reduces flexibility. For rapid development and to incorporate a wider range of algorithms (like experimental ones from the research toolkit), we can enable a **safe scripting or WebAssembly extension** mechanism. One idea is to embed a Python interpreter or a Lua engine into Geode for UDFs. This would let power‑users write a Python function (using NumPy, SciPy, etc.) to do custom transforms or anomaly logic and have Geode execute it on the server side. However, calling Python for each data chunk might not meet our performance targets – the overhead of the interpreter and GIL could be significant at 50k samples/sec. A more performant alternative is **WebAssembly (WASM)**: we could allow users (or developers) to compile anomaly detection routines to WASM and then load them into Geode’s runtime. WASM can execute at near‑native speed and provides sandboxing. For instance, a developer could implement a wavelet‑based anomaly detector in Rust, compile to WASM, and register it as `anomaly_detect_wasm("my_detector", series)` in Geode. The database engine would pass the series data to the WASM module for processing. This approach is increasingly used in databases to allow custom code execution with safety. It gives us the flexibility to plug in new or domain‑specific detection algorithms without rebuilding the entire database engine. The downside is complexity in implementation and possibly less efficient memory access compared to pure native code. As a middle ground, we might provide built‑in support for the most common algorithms (FFT, SR, thresholds, CUSUM, etc.) natively, and use a WASM plugin mechanism for less common or evolving techniques.

### GPU Acceleration

To meet the highest throughput needs, especially if we want to analyze many series in parallel or very high‑frequency series, we will leverage **GPU acceleration** where available. The Geode design already accounts for optional GPU offload for heavy operations like very large FFTs or vector math \[13]. We will follow the same paradigm: if a GPU is present, certain spectral transforms can be offloaded. For example, a large spectrogram (many FFTs on sliding windows) or correlation across hundreds of thousands of points could be computed on a CUDA kernel much faster than on CPU \[13]. The integration can be done by marking these operations in the query planner – if data size exceeds a threshold, or if the system is under heavy load, the operation is dispatched to a GPU module. We’ll ensure that overheads like data transfer are minimized (e.g., compress data on CPU, send to GPU, decompress and compute, as suggested in Geode’s design notes \[13]). For anomaly detection algorithms like CNNs, using the GPU could also significantly speed up inference. A model like SR‑CNN could run an order of magnitude faster on a GPU, meaning even if we had to evaluate it for many series concurrently, we stay within latency bounds. Overall, the strategy is to make the anomaly detection module **hardware‑aware**: use SIMD vectorization on CPU for things like filtering and CUSUM, and tap into GPU for massively parallel tasks or deep learning inference when available.

In summary, we plan a modular extension of Geode with signal processing capabilities: a core library of native transforms and detectors for performance, augmented by an extension framework (WASM or similar) for flexibility, and tuned to exploit hardware acceleration. All of this will be encapsulated within Geode’s engine or provided as loadable modules, so from the user’s perspective, these are just additional query functions or background services within the database. This approach keeps the analysis “close to the data,” eliminating the costly export of time‑series to external tools and thereby supporting real‑time anomaly detection at scale.

## Representing Anomalies in the Graph Schema

Once anomalies are detected, we need to represent the results inside Geode’s graph model in a way that is queryable and meaningful to analysts. We considered three options: (1) tagging anomalies as attributes on existing nodes, (2) creating anomaly indicator edges, or (3) modeling anomalies as separate nodes. We recommend using **dedicated `AnomalyEvent` nodes** linked to the relevant entity in the graph, as this provides the most flexibility for analysis.

In Geode’s data model, each device (or monitored entity) is a node which has one or more `Series` nodes (time‑series) attached \[2]. We will introduce a new node type, say `AnomalyEvent`, to represent an occurrence of anomalous behavior in a time‑series. Each `AnomalyEvent` node would contain properties such as:

- the timestamp or time interval of the anomaly,
- the anomaly score (or confidence),
- the detection method that flagged it (e.g., `"FFT-threshold"` or `"SR-CNN"`), and
- a brief classification (e.g., `"beaconing pattern"` or `"volume spike"`).

When an anomaly is detected on a particular series, the system will insert a new `AnomalyEvent` node and connect it via a relationship to the `Series` node that it pertains to. For example, if series `S` (metric `"bytes_out"` of device `D`) has an anomaly at time `T`, we create:

```
(A:AnomalyEvent { ts: T, score: 0.95, type: "spectral_peak" })
```

and create an edge:

```
(:Series)-[:ANOMALY_DETECTED]->(:AnomalyEvent)
```

linking `S` to `A`. Through the existing `Device–Series` link, the anomaly is implicitly connected to the device as well (`Device D → Series S → Anomaly A`). This allows graph queries to traverse from a device to its anomaly events or to find all devices with anomalies of a certain type.

Representing anomalies as separate nodes has multiple advantages. First, it naturally accommodates multiple anomalies over time – we expect each series to potentially have many anomaly events, and storing these as distinct nodes avoids polluting the device or series node with an ever‑growing list of timestamps or scores. Instead of a single property that must hold a complex history, each anomaly is an entity we can query and update. Second, anomaly nodes can be richly attributed and connected: we can attach additional context as needed, such as links to what triggered the alert. For instance, if an anomaly corresponds to a specific pattern (like a known malware beaconing signature), we could link the `AnomalyEvent` node to a **Knowledge‑Base** node describing that pattern. Or if multiple anomalies are related (say, a sequence of anomalies across different series that together indicate a multi‑stage attack), we could connect those `AnomalyEvent` nodes to a higher‑level **Incident** node or simply find them via queries. This graph representation makes it easier to answer questions like “find all anomalies in the past hour across all sensors in the same subnet” or “check if an anomaly on device A preceded an anomaly on device B it’s connected to”. If anomalies were only flags or properties, these graph queries would be harder.

We did consider simpler approaches: for example, adding a boolean `is_anomalous` flag or `last_anomaly_ts` directly on the `Series` or `Device` nodes. While we might still do this for quick filtering (e.g., a `device.anomaly_score` property that tracks the most recent score), it’s insufficient for detailed analysis because it loses historical anomalies and context. An intermediate approach is using anomaly edges with properties – e.g., an edge from `Device` or `Series` to itself or a ghost node, carrying anomaly info as a property. This is essentially equivalent to a node in terms of complexity, but less clear structurally (since edges are not first‑class query results in GQL like nodes are). Therefore, our design sticks with explicit `AnomalyEvent` nodes.

In terms of schema, we will extend Geode’s type system to recognize these anomaly nodes and edges. They may be tagged with a label like `:Anomaly` or `:Alert`. We also ensure they fit into Geode’s temporal model if needed (since Geode supports bi‑temporal versioning of graph entities). An anomaly has an **occurrence time** (domain time) which we will store as a property, and it might also have a **detection insertion time** (when it was written to the DB). If needed, we can leverage Geode’s existing temporal features so that anomalies can be queried “as of” a certain time (e.g., an as‑of query to see what anomalies were known up to last week). However, given anomalies are events, simply storing their timestamp might suffice.

When the anomaly detection logic runs (whether in real‑time or via a query), it will output anomalies either directly into the graph or to the query result. For continuous detection, we will likely have it insert anomaly nodes as part of the materialized view or trigger. This effectively makes Geode perform a graph write (inserting a node and edge) from within the time‑series ingest pipeline. Geode’s transaction infrastructure can handle this – since all writes go through the WAL and partitioner, adding a couple of writes per anomaly is minor overhead. We will take care that these anomaly insertions don’t create too much back‑pressure; however, anomalies should be relatively infrequent compared to raw data points (especially if the false alarm rate is controlled to \~1 per hour per host as the research aims \[17]). Thus, the volume of anomaly nodes is much smaller than the volume of time‑series points, so storing them as graph entities is reasonable.

Finally, by storing anomalies in the graph, we can leverage Geode’s **security and access control** for them just like any other data. Role‑based access control might restrict who can see certain anomaly alerts (e.g., only SOC analysts can see high‑criticality anomalies), and graph traversal algorithms (like path finding or community detection) could incorporate anomalies as signals in broader analysis (for example, finding subgraphs that exhibit many **correlated anomalies**). In essence, anomalies become first‑class citizens of the data model, which aligns with Geode’s philosophy of **unifying graph and time‑series** information.

## Performance Considerations for Real‑Time Detection

Embedding a sophisticated anomaly detection pipeline in Geode requires careful attention to performance, to meet the target of \~50,000 samples/sec with sub‑200 ms detection latency \[12]. We break down the performance factors and how we address them:

### Throughput and Parallelism

Geode’s architecture is already optimized for high ingestion rates (tested ≥2 million points/sec per node) \[6] and fast query scans via chunked storage. Anomaly detection will introduce extra computation per data point or per window, which could be intensive if done naïvely. However, we exploit **parallelism at multiple levels**. Each series can be processed independently in most cases – if we have dozens of series each at high rate, Geode (being partitioned by device or series ID) will naturally distribute them across threads or cluster nodes. This means the 50k samples/sec load can be split among cores. If, instead, a single series is pushing 50k points/sec (e.g., a single high‑frequency sensor), we will use **window batching** to group points for analysis. For instance, rather than recompute an FFT for every single new point, we might compute it for each batch of, say, 4096 points (the chunk size) or use a sliding window that updates every _N_ points. This reduces the invocation overhead. Geode can handle sequential writes quickly; the limiting factor becomes the analysis compute. By tuning window sizes and batch intervals, we ensure we don’t run analysis more often than needed. We can also allocate a **dedicated thread pool** for anomaly computations so that these tasks do not contend with normal query execution threads. This isolation ensures that heavy spectral calculations do not delay transactional graph operations and vice versa.

### Algorithmic Efficiency

The chosen transforms and detectors must be efficient. Fortunately, many signal transforms have optimized algorithms (FFT is _O(N log N)_, wavelet transforms can be _O(N)_, etc.), and the window sizes of interest are moderate. For example, computing a 4096‑point FFT on modern hardware can take only a fraction of a millisecond with optimized libraries, and even a continuous wavelet transform on a few thousand points (with tens of scales) might execute in a few milliseconds in C. Anomaly detection algorithms like **CUSUM** or **thresholding** are trivial in cost. More complex ones like **matrix profile** or **robust PCA** are far more expensive (matrix profile is _O(N²)_ for naive computation, though there are approximation techniques). Such heavy algorithms would likely be used only on‑demand over limited intervals, not in the continuous 50k/sec stream. We will document which algorithms are supported in **streaming mode** (those that are lightweight and incremental) versus those only for **offline analysis**. For instance, **Spectral Residual** is very fast (essentially one FFT plus vector subtraction) so it’s suitable for real‑time; SR‑CNN adds a CNN inference which is also fast if the model is small (a CNN with a few conv layers on a sequence of length, say, 256 residual points can run in <1 ms on CPU). On the other hand, a full **Hilbert–Huang Transform (EMD)** could take seconds for a long series and is not feasible at high frequency – that might be restricted to a specialist query rather than continuous use. We will leverage **streaming‑friendly algorithms** like **ARIMA** forecasting (which updates state each time‑step), change detection which accumulates statistics, and sketching techniques for any expensive operations (e.g., if we ever approximate matrix profile or PCA, we’d use incremental methods or limit the subsequence length). In summary, our pipeline will prioritize algorithms with linear or near‑linear complexity on the window size to maintain throughput.

### Memory and Data Movement

Real‑time analysis also puts pressure on memory and I/O. Geode’s **chunk cache** holds recent points in memory, so our detection modules can often operate on in‑memory data without extra I/O. We will ensure that when an analysis window spans multiple chunks (say an anomaly window covers two chunks), the system can still retrieve those points efficiently (possibly by a multi‑chunk read that is still largely sequential in memory). We will also be mindful of **data copying**: for example, when using a library or offloading to GPU, we should pass pointers to existing arrays if possible rather than copy large buffers. If using WASM or Python, data copying could be a concern; we would use **zero‑copy interfaces** (like Python C‑API buffer protocol or WASM memory mapping) to avoid redundant moves of time‑series arrays. The anomaly detection module will likely maintain some **state per series** (for incremental algorithms like running mean, ARIMA state, etc.). We will store this state in a lightweight structure keyed by series, so that each new point’s arrival can quickly update the state without recomputing from scratch. This is critical for keeping up with high rates – e.g., an online change detector can be updated in _O(1)_ per point, whereas recalculating over a large window each time is unnecessary.

### Real‑Time Constraints and Scheduling

Achieving ≤200 ms end‑to‑end latency means from the moment data arrives (or a window closes) to the moment an anomaly is flagged, the processing must complete within that time bound. We will design the system to handle this even under load. One tactic is to use **micro‑batching with deadlines**: for example, process new data in 100 ms batches, leaving a cushion for output and any variance. If the load is too high to meet the deadline, the system can adapt by either **simplifying the analysis** (e.g., skip a heavy algorithm and fallback to a simpler one when overloaded) or by **scaling out** (if running in a distributed cluster, shift some series to another node, or spin up a GPU task). Because Geode can **throttle ingestion via back‑pressure (QUIC flow control)** when the system is overloaded \[11]\[18], in worst‑case scenarios the data rate can be effectively slowed to what the anomaly pipeline can handle, ensuring it doesn’t fall arbitrarily behind. Of course, our goal is to handle the target rate without throttling by having sufficient compute resources. A modern 16‑core server with optional GPU should comfortably handle 50k points/sec of analysis, given that’s only \~3,125 points/sec per core if perfectly balanced, and each core can do far more operations per second than that (billions of ops). Our testing will verify that even with realistic overhead (context switches, other queries), the pipeline stays within latency. If needed, we can **pin certain threads to CPU cores (affinity)** to reduce jitter for the real‑time tasks.

### Validation with Workload

We will benchmark using realistic cybersecurity data (as per the research datasets). This means testing scenarios like bursty network traffic or IoT telemetry streams to ensure detection keeps up. The research target of **5 minutes median Time‑To‑Detect** for critical threats \[19] should be easily met if our pipeline always responds within 0.2 sec once the pattern emerges. The more challenging metric is the **false alarm budget (≤1 false per hour)** \[17], which relates to accuracy rather than performance. However, performance can indirectly affect this: e.g., if the system is too slow and has to drop or summarize data, it might miss anomalies or introduce noise. By keeping the full fidelity of data in our transforms (thanks to Geode not dropping points by default \[14]), we maintain detection accuracy while meeting throughput.

In summary, the system is engineered to handle the heavy lifting of spectral analysis in real‑time by using efficient algorithms, parallel/distributed processing, and hardware acceleration as needed. Geode’s existing performance optimizations (like skipping irrelevant chunks, vectorized execution, and potential GPU use) provide a head start. Our additions will extend these to the anomaly domain, ensuring that even with added computational workload, the database can produce anomaly alerts swiftly and at scale.

## Implementation Roadmap and Trade‑Offs

Building this integrated anomaly detection capability in Geode will be an incremental process. We propose a phased implementation roadmap along with considerations of embedding the logic in the database versus using external services:

### Phase 1 – Prototype and API Design

In this phase, we implement basic versions of the key components and expose them as new query functions or procedures. For example, we might start with a simple FFT‑based anomaly detector: a function `anomaly_score_fft(series, interval)` that computes an FFT on the series over the given time interval and returns an anomaly score (perhaps using spectral residual or a threshold on a particular frequency). We’ll also create a function like `flag_anomalies(series, method)` that returns a set of time ranges or points that are anomalies as per the chosen method. Initially, these could be implemented in a straightforward (even non‑optimized) way in Geode’s codebase to validate correctness. We will use small datasets to test if the anomalies found make sense (comparing with the research’s Python toolkit results). During this phase, we also design the graph schema extensions (`AnomalyEvent` nodes and edges) and possibly implement a procedure to persist results: e.g., `INSERT_ANOMALIES(series, method, window)` which under the hood calls detection logic and writes any found events to the graph. By the end of Phase 1, we aim to have end‑to‑end capability on a small scale: an analyst can run a query or command in Geode and get anomaly outputs, and we confirm that these outputs align with expectations from known anomalies in test data.

### Phase 2 – Real‑Time Integration (Continuous Detection)

Here we focus on hooking the detection into the ingestion pipeline for automatic, low‑latency anomaly flagging. We will extend Geode’s **streaming query mechanism** or implement a custom background worker that subscribes to time‑series inserts. One approach is to utilize Geode’s **materialized view (MV)** or **continuous query** concept \[9]\[20]. For example, we define a continuous query that for each new point or each new window of points on a series, evaluates the anomaly detection function and, if an anomaly is present, emits a result (which could then trigger insertion of an anomaly node). Geode might not yet have a full materialized view feature, so we may simulate this by running a dedicated thread that periodically queries recent data and checks for anomalies (this is a bit like polling). Alternatively, since the design explicitly mentions capturing time‑series inserts via **CDC** \[11], we could intercept those events in the server and directly call our detection routines. We will need to manage state carefully – e.g., for a streaming CUSUM, maintain the running mean and variance for each series as state between inserts; for window‑based methods, accumulate points until the window is full. Phase 2 will involve optimizing these routines so they can run continuously without slowing down ingestion. We’ll test on increasing data rates, tuning parameters (like window sizes, batch sizes) to ensure we stay under the latency budget. By the end of this phase, Geode should be able to automatically create `AnomalyEvent` nodes/edges in near real‑time as data streams in, effectively turning it into an intelligent graph+timeseries system that not only stores data but interprets it on the fly.

### Phase 3 – Advanced Methods and Scaling

With the basics working, we move to incorporate more of the advanced techniques from the research and ensure the system scales out. This includes integrating the **SR‑CNN** model for certain metrics (which means choosing a small CNN architecture, training it outside or using a pre‑trained one, and hooking it up with an inference engine in Geode). We will also look at **multi‑variate or correlation‑based detection** – for instance, if an anomaly is only clear when comparing two series (like two sensors that normally correlate but diverge during an incident). This might involve extending detection functions to accept multiple series or to analyze an entire subgraph. We also consider adding more spectral methods: e.g., **Welch’s method** for spectral density (averaging FFTs of subwindows), or a **configurable wavelet transform** where users can choose the wavelet family and scale range. Each addition will be evaluated for performance impact. If some methods are too slow for real‑time, we’ll document them as “offline use only” or ensure they only run on coarse‑grained data (e.g., daily aggregates). During Phase 3, we also **stress‑test** the system in a distributed scenario: multiple Geode nodes handling different parts of the graph, each doing local anomaly detection. We’ll verify that our approach scales horizontally (more nodes can monitor more series) and that global latency constraints are met (the slowest node’s detection still meets the 200 ms envelope). Additionally, we refine the user interface – possibly adding convenience, such as an `ANOMALIES()` table function that a user can query to get all recent anomalies, or integration with Geode’s **alerting/notification** subsystem if it exists (so that when an anomaly node is created, a notification could be sent out to an external system or user).

### Phase 4 – Hardening and User Adoption

Finally, we will harden the solution for production use. This includes extensive testing with real workloads, ensuring memory usage is stable (no leaks in continuous detection), and perhaps providing tooling to **manage the anomaly detection configuration**. For example, DBAs might want to enable or disable certain detection algorithms per series or adjust sensitivity (thresholds). We might introduce a configuration syntax, e.g., attach a policy to a `Series` node like a property:

```json
{ "method": "SR-CNN", "threshold": 0.9 }
```

which the engine uses to decide what to run. We will also implement **monitoring** for the detection process itself – measuring how much time is spent in detection per second, how many anomalies are being generated (to watch false positive rates in real deployments), etc. **Logging and explainability** are also important: if an anomaly is flagged, we should be able to provide insight (the research emphasizes interpretability \[21]). We can store in the `AnomalyEvent` node not just a score but maybe a pointer to **feature attribution** – e.g., which frequency component was high. This could be a small vector or description that analysts can examine to validate the alert. In Phase 4 we also weigh the **maintenance trade‑offs**: every new native feature means more code to maintain in Geode (which is acceptable if the value is high). If we find that some algorithms are rarely used or too costly to maintain, we might instead support them via the plugin interface (letting advanced users plug in Python or WASM modules for niche cases).

Throughout these phases, an important consideration is the trade‑off between embedding logic inside Geode versus using external microservices. By **embedding**, we get low‑latency access to the data (no need to ship data out to an external process), atomicity (the ability to insert data and mark an anomaly in one transaction potentially), and a simplified deployment (one system instead of a pipeline of multiple components). This tight integration is aligned with our goal of **unified analytics** \[7]. However, embedding increases the complexity of the database engine. We are essentially adding some domain‑specific analytical capabilities to a general‑purpose DB. If not carefully modularized, this could make upgrades or changes harder. There’s also the risk that a bug or heavy load in the anomaly detector could affect the core DB operations. We mitigate that by **isolating threads** and perhaps allowing the anomaly feature to be toggled off if needed (so that in a worst‑case scenario, the DB can operate as a plain TS store without analysis).

On the other hand, an **external microservice** approach could leverage the rich ecosystem of data science tools – for example, directly using the Python toolkit developed in the research \[22] or libraries like PyOD, without reimplementing in Zig. It also allows **independent scaling** (you could scale up the detection service separately from the DB). The clear downside is latency and consistency: the external service would receive data via network (even if using CDC, there’s network I/O and serialization), and any result it produces must be sent back to Geode to be stored or acted upon. This round‑trip is likely tens of milliseconds at best, and more if the volumes are large, eating into our 200 ms budget. Also, if the external system goes down or lags, anomalies might be missed or delayed. We prefer to avoid these issues by keeping the **critical path in‑process**. That said, we can still incorporate some ideas from the microservice approach: for example, using a message queue (like Kafka) for buffering might inspire how we buffer points internally before analysis, or using a model server could inspire how we isolate the CNN inference.

A **hybrid approach** might be to embed a minimal inference engine (for speed) but allow training or heavy computation to be external. For instance, training a new anomaly detection model (say a new autoencoder on historical data) could be done outside and the resulting model coefficients loaded into Geode. This way, Geode does the fast part (applying the model) and external tools do the slow part (training or extensive analysis). This division of labor is common in systems that deploy machine learning in production.

In conclusion, the trade‑offs favor **embedding the runtime detection logic** within Geode for performance and seamlessness, while using external tools for development, tuning, or non‑real‑time analysis. The roadmap reflects this: build up internal capabilities step by step, ensure they meet performance targets, and use external pipelines only as an optional supplement. By following this plan, we expect to transform Geode into a powerful platform that not only stores graph and time‑series data together but also intelligently analyzes streaming cyber‑data for anomalies in real‑time – a capability that would significantly enhance security monitoring use cases.
