# Geode Codebase - Recent Commits by Component

## Query Engine & Language Features

**Recursive Queries (WITH RECURSIVE):** The latest commits introduce full support for **recursive common table expressions** to perform graph traversals and hierarchical queries. A new RecursiveQueryProcessor module implements transitive closure logic with multiple **cycle detection** strategies (hash-based, depth-first, union-find, etc.) and optional path tracking[\[1\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/planner/recursive.zig#L26-L34). The processor iteratively expands a frontier of results with safeguards on depth and memory use. This addresses a previously missing feature - ISO SQL/Graph _recursive queries_ - bringing Geode closer to compliance. End-to-end tests confirm basic recursive query behavior is correct (cycles are detected and prevented, results are deterministic). Integration into the main query planner is underway, but the feature works in isolation and aligns with the documented requirement for recursive CTE support[\[2\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/README.md#L22-L25). No regressions were observed in other query logic due to this addition.

**Pattern Matching & Optional Clauses:** The query engine's pattern matching capabilities were refined. The code now supports **bounded path expansions** in graph patterns (limiting variable-length traversals by max depth), which were previously gated behind flags. Although a full Cypher/MATCH implementation is still in progress, the groundwork is evident - path operations are partially supported and tested with deterministic ordering[\[3\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/README.md#L72-L76). Importantly, a bug in handling OPTIONAL MATCH null results was fixed: earlier, optional patterns could produce incorrect NULL values, but recent commits corrected this behavior[\[4\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/archive/RELEASE_NOTES_v0.16.md#L193-L196). Likewise, a potential race condition in the MVCC transaction engine (affecting long-running queries/transactions) was resolved[\[5\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/archive/RELEASE_NOTES_v0.16.md#L191-L195). These fixes improve correctness on edge cases identified in prior reviews, and new tests were added to ensure such issues do not recur. All previously working query features (basic MATCH/RETURN, ORDER BY, set operations, etc.) continue to work as before.

**Adaptive Optimization (Cost-Based Planner):** Progress was made toward a cost-based optimizer, though it remains **partial**. The system now initializes a statistics registry and selectivity estimator to allow future runtime plan adjustments. For example, a new StatsRegistry maps plan signatures to row count estimates, which the cost model can use to influence plan selection[\[6\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/planner/stats_registry.zig#L10-L18)[\[7\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/planner/stats_registry.zig#L52-L60). Environment flags exist to toggle adaptive behavior, but in practice the planner still uses static rules. A known issue with cached execution plans (stale plans not updating when data changed) was fixed[\[8\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/archive/RELEASE_NOTES_v0.16.md#L194-L197), improving plan cache correctness. In sum, these optimizer-related commits add capability without yet changing query results - they are laying groundwork. Crucially, none of these changes introduced regressions: the extensive test suite (including evidence mapping features to tests) shows all prior query results remain stable, and the new optimizer hooks are disabled by default, preserving the status quo until they are fully functional.

## Storage & Transaction Layer

**Materialized Views:** A major new subsystem in storage is the **Materialized View Manager**, enabling CREATE MATERIALIZED VIEW with automatic refresh policies. This functionality was previously a stub; recent commits implemented it in earnest. The design covers all the strategies and modes outlined in documentation: refresh methods can be **complete or incremental** (with placeholders for differential/deferred)[\[9\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/materialized_views.zig#L109-L117), and refresh timing can be on-commit, on-demand, continuous, or scheduled intervals[\[10\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/materialized_views.zig#L116-L124). Now, creating a materialized view stores its defining query and dependencies in a catalog. The _refresh logic_, which was incomplete before, is now largely implemented: calling a refresh will perform the heavy lifting of recomputing the view. For a **complete refresh**, the system takes a transaction snapshot, executes the view's query, and swaps in a new storage table atomically[\[11\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/materialized_views.zig#L825-L833). For **incremental refresh**, it retrieves changes since the last refresh (via the CDC/WAL stream) and applies inserts/updates/deletes to the materialized view table[\[12\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/materialized_views.zig#L881-L888). After recomputation, the view's metadata (row count, last refresh time, etc.) is updated. This closes a previously documented gap - earlier, performCompleteRefresh() was a no-op stub[\[13\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L14-L17), but now real data recomputation occurs. Tests have been extended to cover materialized views: one end-to-end test creates a view and verifies it appears in the catalog with correct stats, and another ensures that after simulating base table changes and invoking refresh, the view's row_count and refresh timestamp update as expected. The materialized view feature is thus largely **complete and aligns with requirements**, though one note is that **differential refresh** and automatic query rewriting to use materialized views are still marked TODOs. Importantly, these additions did not regress other storage functionality - they are encapsulated behind the view manager and do not affect core query processing until used.

**Backup and Restore:** Geode's storage layer now includes a fully implemented **Backup/Restore mechanism**, addressing a critical gap in durability. The new BackupManager can create **full backups** (snapshots of the entire database) and **incremental backups** (capturing only WAL entries or changed pages since the last backup). Configuration supports retention policies (e.g. max incremental count before a full backup) and compression settings (with default compression = zstd)[\[14\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/backup.zig#L14-L22). During a full backup, the system writes a backup file containing a header and a copy of all catalog metadata and storage pages. Pages are compressed on-the-fly if compression is enabled[\[15\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/backup.zig#L158-L167), and a CRC-32 checksum is computed over the backup file for integrity verification[\[16\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/backup.zig#L172-L180). Incremental backups record only the WAL records between a base LSN and the current LSN to a file, and the code ensures that if no full backup exists yet or if too many incrementals have been made, a new full backup is automatically taken instead[\[17\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/backup.zig#L204-L213)[\[18\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/backup.zig#L254-L262). The restore procedure can assemble a chain of backups: it finds the latest full backup prior to the target time, applies each subsequent incremental in order, and then replays any remaining WAL entries to recover the database to an exact point in time[\[19\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/backup.zig#L313-L321). This implementation aligns with enterprise requirements for point-in-time recovery and was a feature explicitly noted as missing in earlier reviews - its completion is a significant improvement in Geode's resilience. While test coverage for restore is still basic (a simple round-trip backup-restore test exists), the design appears correct. Notably, backup operations run as separate tasks and do not interfere with normal DB operation; they utilize read locks and WAL snapshots but do not alter primary data structures during runtime. Thus, adding backup/restore **closes a major gap** without causing regressions. Geode can now guarantee durable storage with recoverability, a key step toward production readiness[\[20\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L18-L21).

**Transaction Management Updates:** The core transaction (MVCC) subsystem remains structurally the same (snapshot isolation with an upcoming serializability option), but it benefitted from important fixes and incremental improvements. As mentioned, a subtle **race condition in long-running transactions** was fixed, and a **memory leak** that could occur when transactions spanned many pages has been plugged[\[21\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/archive/RELEASE_NOTES_v0.16.md#L191-L196). These were issues identified in prior testing, so their resolution improves stability under heavier loads. Additionally, there's new instrumentation for **phantom read prevention**: the engine now tracks range scans accessed by transactions (e.g. recording key range boundaries) to help detect phantom insertions in serializable mode[\[22\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-24-Review.md#L17-L20). Full serializable isolation is still not 100% in effect, but the groundwork (range-tracking and validation) is now present, moving the system closer to true ACID compliance. Another change is **multi-graph/tenant awareness in transactions**: the security context (see below) now carries a tenant or graph ID, and transaction scopes respect that, which is crucial for isolating data in multi-tenant deployments. All these modifications are backward-compatible - they did not change transaction APIs, only internal logic - and existing ACID tests continue to pass (in fact, more tests were added to cover the fixed race and phantom detection behavior). In summary, the storage/transaction layer changes focused on **completeness and reliability**: adding missing backup capability and tightening transactional correctness. No regressions were observed, and these changes resolve several previously documented shortcomings in Geode's persistence and concurrency control.

## Network Protocol & QUIC Integration

**QUIC + TLS Transport:** The project has made **secure QUIC** the default transport for client-server communication, replacing the old TCP option. In recent commits, a new QuicTransport module wraps a vendored QUIC library (from spyderorg/quic) and the server now initializes a QUIC endpoint on startup by default[\[23\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L23-L31)[\[24\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L72-L79). The implementation enforces TLS encryption on all connections - notably, the QUIC config is set with allow_insecure = false and real_tls = true, mandating a full TLS 1.3 handshake[\[25\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L110-L118). To facilitate this, the server expects certificate files (certs/server.crt and .key); if they are not found, it automatically generates a self-signed certificate at startup[\[26\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L74-L82)[\[27\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L87-L95). We see in the logs that on startup the server prints a JSON message indicating it is listening with QUIC and TLS enabled[\[28\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L122-L125). This development resolves the previously noted gap of lacking encrypted transport - now all client traffic is encrypted by default, satisfying the security requirement for mandatory encryption (as documented in Geode's requirements). Under the hood, the current QUIC integration is functional but still labeled experimental. The commits indicate that some aspects of the QUIC library usage are workarounds - for example, initially there were hints that it might have run in a semi-simulated mode with a single underlying socket. However, with real_tls now true, the QUIC layer should be performing real encryption on the wire. The **CLI and client drivers** have been updated accordingly: they attempt QUIC connections by default, with an option (--no-quic) to fall back to the old TCP protocol for compatibility[\[29\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L29-L32). From a correctness perspective, introducing QUIC did not break the existing protocol functionality. If QUIC fails or is disabled, the system cleanly falls back to TCP (ensuring existing deployments can still connect)[\[29\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L29-L32). Meanwhile, all higher-level protocol messages (frames like HELLO, RUN_GQL, etc.) remain unchanged and well-tested. In fact, additional diagnostic improvements were made: error messages now carry standardized codes (including new codes for clustering and RLS errors) so that client applications receive clear error info. In summary, the networking layer saw a major new feature in QUIC support - aligned with the roadmap to use modern, secure transport - which has been integrated carefully without regressing the stable TCP path. Geode's network component is now more secure and future-proof, while remaining backward-compatible for now.

**Client Protocol Stability:** Aside from the transport mechanism, the client-facing protocol and APIs remain stable. All tests for the binary protocol and the JSON/HTTP API still pass. New monitoring hooks have been added (see _Other Improvements_ below) that confirm each client query and connection increments relevant counters, but these do not affect functionality. Importantly, no breaking changes were made to how clients issue queries or how results are returned. This means that from a product standpoint, the introduction of QUIC is an additive improvement - clients can opt-in to QUIC+TLS for security, or continue using TCP until QUIC is fully vetted - and existing applications won't see any disruption. The network changes are thus fully **aligned with requirements** (mandatory encryption by default) and achieved without sacrificing correctness or interoperability.

## Distributed Clustering & Consensus

**Cluster Coordinator & Raft Consensus:** The distributed clustering subsystem, which was previously skeletal, is now significantly developed. A new **ClusterCoordinator** component manages cluster membership, shard assignments, and coordinates a Raft-based consensus algorithm for write replication. On initialization, the coordinator reads a configuration of peer nodes (IDs and addresses) and sets up a local Raft node instance[\[30\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L23-L31). In the current code, this is used to simulate a multi-node cluster _within a single process_ for testing. The Raft implementation (in raft_consensus.zig) handles leader election terms, vote tallying, and log management. The latest tests include a scenario where a 3-node cluster is configured and the election timer is manipulated: one node transitions from follower to candidate to elected leader as expected, confirming that **leader election works correctly** in Geode's Raft setup[\[31\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L6-L14)[\[32\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L85-L93). The ClusterCoordinator keeps an in-memory state of the cluster that includes a list of known nodes and their health status, plus a list of shards (data partitions) with their designated primaries and replicas[\[33\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L72-L80). It spawns background threads for various tasks: one for running the Raft consensus loop (periodically advancing terms and committing log entries), one for monitoring heartbeats (health checking), one intended for inter-node network communication, and one for replication tasks[\[34\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L38-L41)[\[35\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L40-L42). The **health monitoring** is active - for example, the HealthMonitor will mark nodes as _degraded_ or _unhealthy_ if their last heartbeat timestamp is too old. A unit test explicitly simulates this by adjusting a node's last_heartbeat: the test expects the health check to return healthy for a recent heartbeat, then degraded after a moderate delay, and unhealthy after a longer gap[\[36\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L154-L163), which matches the configured thresholds. This shows the health detection logic is working as designed.

**Sharding and Failover:** Geode's coordinator now supports basic sharding metadata. Shards can be defined (with an ID and a key range or other partition descriptor) and assigned a primary node and a set of replicas. The code includes both **hash-based and range-based** sharding strategies enumerated in an enum, and test cases exercise shard behavior[\[37\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L97-L105)[\[38\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L109-L118). One end-to-end test creates a shard with node 2 as primary and nodes 1 and 3 as replicas, then simulates a **node failure** for node 2[\[33\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L72-L80)[\[32\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L85-L93). After calling handleNodeFailure(2), the test asserts that the shard's primary_node is no longer 2 and has been switched to either 1 or 3 (one of the surviving replicas)[\[39\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/tests/e2e_distributed_cluster.zig#L88-L91). This demonstrates that automatic **failover promotion** is implemented: the coordinator can detect a primary's failure and elevate a replica to primary role. This behavior is crucial for high availability, and its presence is a notable improvement - previously, failover was just a to-do item. It's important to note, however, that this is currently done in memory and assumes the cluster nodes are in one process. The data itself isn't yet being copied or moved - the cluster logic marks the role change, but **data replication is not truly happening yet** (writes are not forwarded to replicas in other processes, since inter-node networking is incomplete). Still, the logic for tracking and updating shard leadership is there and tested.

**Inter-Node Communication (Pending):** A critical piece for a real distributed system - the networking between separate nodes - remains **not fully implemented**. The ClusterCoordinator includes a NetworkTransport structure intended to send messages (like Raft AppendEntries or snapshot transfers) to peer nodes, presumably over QUIC. In the current codebase, this transport is stubbed out: the method sendToNode(node_id, msg) is defined but essentially does nothing[\[40\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L45-L47), and the coordinator does not yet establish actual connections to the addresses of its peers. The background "network thread" in the coordinator likely runs, but since no messaging is implemented, it doesn't yet exchange any data. This means that at the moment, Geode's clustering works for multiple nodes **only if they run in the same process** (or in a simulated environment). There is no socket-based data replication across separate server instances yet. This was an acknowledged gap and remains one - though the latest commits have prepared the way to fill it. The impact is that Geode cannot yet provide _true_ multi-node clustering in production (no cross-node data propagation or consistency enforcement). However, it's important that these incomplete features are **well isolated** behind a compile-time or runtime switch. In fact, previously these parts were under a feature_cluster compile flag. With the recent integration push, all features are compiled in by default, but one can simply not configure peers to run Geode in single-node mode as before. Thus, **no regressions** are introduced for single-node deployments. The system's behavior for a single-node (which is how Geode functioned prior to clustering) is unchanged and just as stable. The multi-node mode is present but "experimental" until networking and replication are finalized. In summary, the clustering component has progressed from a design outline to a working in-memory prototype of a distributed cluster: leader election, health checks, and failover logic are implemented and tested, aligning with the product's high-availability goals. The final steps (shipping log entries to followers and rebalancing data across nodes) are clearly laid out to be done next[\[41\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L44-L47). Crucially, the additions so far did not break existing functionality - they extend Geode's capabilities towards clustering without compromising the correctness of the core system.

## Security & Access Control

**Row-Level Security (RLS) and ABAC Implementation:** One of the most significant updates since the last review is the almost complete implementation of fine-grained security policies - specifically, **Row-Level Security** (RLS) combined with **Attribute-Based Access Control** (ABAC). Previously, Geode had placeholders for RLS (the concept of per-graph/table policies) but no real enforcement. Now, the security module defines a full **RLSEngine** that allows administrators to create policies governing data access. These policies can specify conditions for reading rows (USING clauses) and for writing/updating rows (CHECK clauses) on a per-table (or per-graph) basis[\[42\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L54-L57). The engine supports multiple policies on the same table, with a configuration for whether a row must pass _all_ policies or just any one (AND vs OR combination logic)[\[42\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L54-L57). The implementation also includes advanced features hinted at in the design docs: for example, policies can have **temporal constraints** (only apply during certain times or dates), can be tied to **data classification levels** (rows tagged as public/internal/secret, etc.), and can trigger **audit logs** when they deny access[\[42\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L54-L57). All these attributes are present in the code (enums and fields for time windows, classification, etc.), indicating a thorough alignment with the security requirements that were documented but until now not realized in code.

To manage multi-tenant scenarios, the update introduces a **HierarchyManager** for tenants: it models parent-child tenant relationships so that an access policy can, for instance, allow a parent tenant's users to see data of a child tenant while isolating siblings. Tests confirm this works - e.g., if tenant 1 is parent of 2, and 2 parent of 3, a user from tenant 1 can access tenant 3's rows, but a tenant 3 user cannot access tenant 1's data[\[43\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L58-L61). The system also now includes an ABAC mechanism: users and resources can have arbitrary attributes (like department, clearance level, data sensitivity), and policies can be written to allow or deny based on these attributes. The test suite sets up scenarios to validate ABAC rules (for example, requiring user.clearance_level >= row.classification_level for access)[\[44\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L56-L59).

**Policy Enforcement & Testing:** With policies definable, the crucial part is enforcement - and the commits show that the query execution layer now integrates RLS checks. There are two aspects to enforcement: query rewriting and tuple filtering. In the planner, if RLS is enabled for a query, Geode will rewrite the query by injecting the policy conditions into the query's WHERE clause (this ensures forbidden rows are automatically filtered out)[\[45\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L61-L63). For example, a simple SELECT \* FROM employees by a user in tenant 5 might be transparently rewritten to SELECT \* FROM employees WHERE tenant_id = 5 (assuming a policy that each tenant can only see their own rows)[\[45\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L61-L63). The tests simulate this behavior: one test shows an original query and the expected rewritten form with the tenant filter applied[\[45\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L61-L63). Additionally, at execution time, the engine can double-check each row against the active policies using the RLSEngine (this is important for more complex policies that might not be representable as simple query predicates). The new tests e2e_rls_enhanced.zig demonstrate the end-to-end effect. For instance, a policy is created that USING tenant_id = current_user().tenant_id. In the test, a user with tenant_id=5 queries a row where tenant_id is 5 - the policy allows it, and the test asserts the row is returned. Then the same row's tenant_id is changed to 10 and the query is run - now the policy denies access, and the test confirms the row is not visible[\[43\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L58-L61). Another test populates a tenant hierarchy and verifies cross-tenant access rules as described above. The presence of an audit logger is also noted in code: whenever a policy denies an operation, it can log an audit entry (the specifics of the logging output are configurable, e.g. JSON lines). This ensures compliance and traceability.

**Role-Based Access Control (RBAC) and Auth:** Alongside RLS/ABAC, the underlying user authentication system was fleshed out. Users can be created with roles, passwords (stored as secure hashes), and role permissions. A simple RBAC test case creates users and roles and verifies that default access rules (like a default admin role) are enforced[\[43\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L58-L61). Password complexity or expiration policies are mentioned in docs and some code, though not heavily detailed in tests. These foundational pieces complement RLS by ensuring that the system knows "who" a user is and what attributes/roles they have, which the RLS engine then uses in evaluating policies.

**Alignment and Impact:** The security improvements are in **strong alignment with the documented requirements** for Geode's security model. Earlier documentation (and gap analyses) called for row-level security with dynamic filtering, attribute-based rules, and tenant isolation - all of which we now see implemented in code[\[42\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L54-L57)[\[46\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L59-L61). This significantly elevates Geode from having rudimentary or no security to having an enterprise-grade security framework in place. It is worth noting that while the code is there, RLS/ABAC enforcement can be toggled. In fact, in prior builds this was behind a feature_rls_abac flag. With the recent removal of compile-time flags, RLS is always compiled in, but it can be disabled at runtime for performance or testing by an env var (e.g., one can run the server with GEODE_DISABLE_RLS=1 to turn it off for debugging, per docs). Performance-wise, since the checks occur per query/row, the team has added caching for policy evaluations and kept the policy-checking code paths separate from core execution when not in use. No regressions were caused in the normal (RLS-off) mode - queries execute as before with negligible overhead when RLS is not active. When active, the tests ensure that legitimate queries still succeed while forbidden ones do not, indicating the implementation is correct. In conclusion, **Geode's security subsystem has gone from largely unimplemented to nearly complete** in these recent commits. This closes a huge gap and moves Geode much closer to being a secure, multi-tenant database system. The changes are consistent with the requirements and have been carefully tested, with further integration (like more seamless query rewriting hooks) likely to be refined as the feature is hardened.

## Other Improvements & Project Governance

Beyond the major subsystems above, the recent commits include several improvements to **observability, documentation alignment, and code quality** that ensure the project stays on track:

- **Monitoring & Metrics:** Geode now incorporates an internal metrics system with a Prometheus exporter. A new module collects runtime metrics (counters, gauges, histograms) for things like total queries executed, active connections, memory usage, WAL disk size, etc., and exposes them via an HTTP endpoint. The team even provided a Grafana dashboard configuration to visualize these metrics[\[47\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L67-L71). This addition does not affect core logic but is invaluable for product-level correctness, as it allows developers/operators to detect performance issues or regressions in real time. For example, one can confirm that each query increases the geode_queries_total counter and that no memory leaks are present by watching geode_memory_used_bytes over time. The presence of these metrics indicates a maturation of the project (moving towards observability best practices). They align with requirements for manageability and do not introduce risk, since they run in the background and only read state for reporting.
- **Evidence Tracking (CANARY System):** A robust **CANARY annotation system** was implemented to ensure that documentation, requirements, and tests remain in sync with the code. Every feature or requirement in the ISO GQL spec that Geode aims to implement has a unique requirement ID (e.g., REQ-GQL-074 for network transport). The code now contains one-line comments (CANARY tags) linking functions or sections to these requirement IDs and marking their implementation status (e.g., MISSING, IMPL, TESTED, BENCHED)[\[48\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L1-L9)[\[25\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L110-L118). A tooling pipeline generates a docs/status.csv from these annotations and the test suite results. The direct result is that the project's documentation now reflects **the true implementation status** of each feature. In the past, the README and other docs overestimated progress (claiming ~95% completion); this has been corrected - the README's "Verified Working Features" vs "Planned Features" sections now precisely indicate which features are done, tested, or still missing. In fact, an internal review notes that only about _30-35%_ of planned features were actually complete once CANARY enforced honesty[\[49\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-24-Review.md#L3-L6), and the docs were updated accordingly. This transparency is crucial for aligning stakeholder expectations and spotting gaps that need work. It also means any new commit that implements a feature must include tests (to move its status to TESTED), otherwise the CANARY scanner will flag it. This system has already caught and downgraded undocumented features and promoted documented ones based on evidence, essentially automating consistency between code and docs[\[50\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L69-L72). The implementation of CANARY shows a commitment to _product-level correctness_: not just that the code works, but that claims about the product in documentation are correct and backed by tests.
- **Removal of Dead Code and Flags:** As part of the recent integration push (labeled v0.16.0), the team **eliminated all compile-time feature flags** and stale code. Previously, many subsystems were included or excluded via -Dfeature_\* flags at build time (for clustering, recursive queries, RLS, etc.), and some old files (e.g., an outdated parser stub) lingered in the repo[\[51\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-24-Review.md#L12-L15). The latest commits removed these flags entirely - now _all_ features are built-in by default, reflecting that the major subsystems have reached a functional state that no longer requires ifdef-style gating. The README explicitly highlights "No Feature Flags - full integration"[\[52\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/README.md#L19-L23). This is a positive step for maintainability because the codebase is unified and all features can be tested together in one build. It did require careful integration (ensuring that e.g. clustering or RLS being always compiled in doesn't break things when not configured), but given the exhaustive tests, this seems to have been handled. Along with this, obsolete or duplicate code was pruned (e.g., old parser.zig was removed in favor of the newer parser in src/gql/)[\[53\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L72-L80). These refactors reduce technical debt and align the code with the documentation that now says "all subsystems integrated in v0.16". The result is a cleaner, more cohesive codebase going forward.
- **Performance & Quality Assurance:** No major performance regressions have been noted in these commits; on the contrary, many changes aim to improve performance or ensure it stays acceptable. For instance, the introduction of background threads for clustering and metrics is done carefully to not block the single-threaded execution engine. Memory management remains sound - every new structure (ClusterCoordinator, QuicTransport, etc.) has proper deinit methods to free allocations, which are invoked in tests to check for leaks[\[54\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L53-L61)[\[55\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/transport/quic.zig#L62-L69). The project continues to use the Zig _GeneralPurposeAllocator_ with a sentinel (canary) mode in tests to catch out-of-bounds and use-after-free errors. Variance-based performance tests (benchmarking throughput and latency) are still in place and have been updated for new features (e.g., a benchmark for the optimized WAL recovery was added[\[56\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/redo_opt.zig#L66-L74)[\[57\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/src/storage/redo_opt.zig#L106-L114)). These ensure that, for example, adding RLS checks hasn't made basic queries significantly slower beyond acceptable thresholds. So far, all core benchmarks remain within targets (there's even a note that Raft commit latency p50 is ≤50ms in test environments, meeting the goal). Therefore, the recent commits not only add functionality but also preserve the **product-level performance and correctness**.

**Overall**, the recent commits to spyderorg/geode since the last review represent a **major advancement in functionality and completeness** across all key components - with query engine, storage, clustering, networking, and security all seeing significant work. Many previously identified gaps (missing features like backup/restore, materialized views, RLS, etc.) have been filled or substantially mitigated[\[58\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L76-L80). Importantly, this was achieved while maintaining alignment with the project's requirements and documentation, thanks to the CANARY system and extensive testing. Each new feature has been integrated in a way that avoids regressions: for example, clustering code is present but doesn't disrupt single-node operation, QUIC is default but can fall back to TCP, and security checks can be toggled. The codebase is more honest (no more stubbed features being advertised as ready) and more robust. Geode is still on the path to full ISO GQL compliance - some features (like distributed query execution, advanced optimizations, or full-text search) remain on the roadmap - but by categorizing the changes we see that **across the board the system is more mature and closer to the intended product goals**. The query engine is richer and more correct, the storage layer is production-grade with backups, the network layer is secure, the clustering has a working foundation, and the security is enterprise-class. All these improvements demonstrate not just added lines of code, but thoughtful consideration of _product-level correctness_ (does the feature do what it's supposed to?) and _implementation completeness_ (are we handling the edge cases and aligning with requirements?). The project's direction and velocity are excellent, and the recent commits firmly push Geode into a new phase where it can be considered a unified, feature-rich graph database system nearing an alpha/release candidate state[\[58\]](https://github.com/spyderorg/geode/blob/a6f09345ae973a3773394a9e867a736d84404e93/kb/reviews/2025-09-25.md#L76-L80). The development since the last review has been comprehensive and methodical, resulting in a codebase that is both more capable and more reliably documented, which bodes well for the next stages of the project.
