# Geode Graph Database

## Description

Geode is an ISO/IEC 39075:2024 (GQL) oriented graph database written in Zig 0.15.1. Governance automation (freshness + CANARY evidence) tracks implementation reality continuously:

![Evidence Coverage](badges/evidence.svg)

- **607 tracked aspects** (requirements / features / bench targets)
- **365 TESTED aspects** (functional tests – subset includes AdvancedCostModel, RefreshScheduler, InvertedIndexCore, RangeTrackerPhantomPrevention)
- **229 BENCHED aspects** (performance / throughput / latency; sample envelopes: AdvancedCostModelCalibration, MvRefreshLatency, InvertedIndexQueryLatency)
- **6 STUB aspects** and **7 IMPL aspects** (under active governance; see docs/IMPLEMENTATION_REALITY.md for details)

Variance Guards Landed: 70+ (see `docs/VARIANCE_ENVELOPES.md`)

Counts are generated by the automated CANARY scanner (`make governance-check`). The governance checks derive counts from `status.csv` (authoritative) to avoid JSON summary drift.

To refresh evidence after landing new CANARY lines or tests:

```bash
make canary              # regenerate status.json / status.csv
make update-status-hash  # sync GAP_ANALYSIS hash marker
make governance-check    # enforce freshness + strict verification

# Optional governance utilities:
make governance-delta            # JSON list of added/removed REQ IDs (requires status_prev.json)
make governance-dry-run          # Non-failing governance summary (CI preview)
make governance-freshness-prewarn# Warn on approaching 60d freshness (default threshold 50d)
```

### Governance Quickstart (TL;DR)

Run this after adding or updating any CANARY lines, tests, or benches:

```bash
go build -o ./bin/canaryscan ./tools/canaryscan   # build scanner (once per env)
./bin/canaryscan --root . --out status.json --csv status.csv --verify docs/GAP_ANALYSIS.md --strict
sha256sum status.json | awk '{print $1}'           # copy hash into GAP_ANALYSIS marker if changed
make update-status-hash                            # or use the helper to rewrite the marker
zig run scripts/governance_ci.zig                  # full governance summary (same as make governance-check)
```

If strict verify fails, look for:

- Stale CANARY dates (UPDATED older than 60 days for TESTED/BENCHED)
- Hash mismatch in `docs/GAP_ANALYSIS.md` vs fresh `status.json`
- Over-claims in docs not backed by scanner counts

When green, commit the doc updates alongside any new tests to keep evidence and narrative in lock-step.

CI Workflows:

- Governance verification runs on `push`/`pull_request` (see `.github/workflows/governance.yml`).
- Telemetry smoke runs in soft mode by default; set `GEODE_CI_TELEMETRY_STRICT=1` to enforce.
- Nightly governance aggregates evidence, refreshes badges, and appends trends (see `.github/workflows/nightly-governance.yml`).

- ✅ **Set Operations**: UNION (DISTINCT/ALL); INTERSECT / EXCEPT stubs partial (flagged) if present
- ⚠️ **Aggregations**: Limited (COUNT / simple SUM) — advanced agg & spill policies still evolving

### Protocol & Standards

- **Binary Protocol**: HELLO / RUN_GQL / PULL (+ diagnostics) with ISO status codes
- **Policies**: US001 (unordered pagination), UA005/UA006 (path tie-break deterministic)
- **Transports**: QUIC (default) and stdio (local debug). TCP has been removed.
- **Formats**: JSON (default), text/plain

### Change Data Capture (CDC) & Diagnostics

- **Engine**: In-process capture of change events (insert/update/delete) with monotonic sequence.
- **Sinks**: Memory (tests) & File (`cdc.log`) implemented; Kafka/Kinesis/Webhook/PubSub placeholders.
- **Malformed WAL Guardrails**: Warn / abort thresholds via `GEODE_MALFORMED_WAL_WARN_PCT` & `GEODE_MALFORMED_WAL_ABORT_PCT`.
  - Flags: diagnostics include `guardrail_warn_triggered` and `guardrail_abort_triggered` (both **latched** once true).
  - Latched semantics: flags remain true after triggering even if ratio later decreases (preserves audit visibility) until explicitly cleared.
  - Timestamps: `first_warn_ts_ms` / `first_abort_ts_ms` record the first trigger time (0 if not yet triggered). Monotonic relation: warn <= abort when both set.
  - Reset API: `CDCEngine.resetGuardrailState()` clears both flags and both timestamps (counters remain). Use after remediation to re-arm monitoring without losing historical malformed counts.
- **Snapshots & Hashes**: Ring buffer of malformed counts + timestamps; prefix/hash retention for first N malformed payloads.
- **Adaptive Flush (Experimental)**: Optional dynamic batch sizing (`CDCConfig.adaptive_flush`).
- **Diagnostics Frame**: `CDC_DIAGNOSTICS` JSON includes counters, config echo, engine state, snapshots, hashes, version, timestamp, _uptime_, _guardrail_epoch_, _backpressure_, and _pending_backpressure_watermark_.
- **Remote Control**: `CDC_CONTROL { action: "RESET_GUARDRAILS" }` frame resets guardrail flags/timestamps and increments `guardrail_epoch`.
- **Enable**: Set `GEODE_CDC_ENABLE=1` when starting server.
- **Not Production Ready**: Intended for observability / experimentation only.

CDC_CONTROL response examples (stdio):

```bash
# Unsupported action
printf '{"type":"CDC_CONTROL","action":"FOO_BAR"}\n' | ./zig-out/bin/geodec --stdio
{"status_class":"00000","result":{"type":"CDC_CONTROL","action":"FOO_BAR","status":"UNSUPPORTED","guardrail_epoch":2}}

# Engine disabled (no GEODE_CDC_ENABLE)
printf '{"type":"CDC_CONTROL","action":"RESET_GUARDRAILS"}\n' | ./zig-out/bin/geodec --stdio
{"status_class":"00000","result":{"type":"CDC_CONTROL","action":"RESET_GUARDRAILS","status":"NO_ENGINE","guardrail_epoch":0}}

# Valid reset (engine enabled)
GEODE_CDC_ENABLE=1 ./zig-out/bin/geoded --listen-quic 127.0.0.1:7567 &
printf '{"type":"CDC_CONTROL","action":"RESET_GUARDRAILS"}\n' | ./zig-out/bin/geodec --stdio
{"status_class":"00000","result":{"type":"CDC_CONTROL","action":"RESET_GUARDRAILS","status":"OK","guardrail_epoch":3}}
```

Backpressure: The diagnostics payload includes `backpressure` (boolean) and echoes the configured `pending_backpressure_watermark`; when `pending_events >= watermark` the flag is `true` and producers SHOULD throttle or force a flush (future API) before pushing more writes.

#### CDC Environment Variables

| Variable                                | Effect                                                 |
| --------------------------------------- | ------------------------------------------------------ |
| `GEODE_CDC_ENABLE`                      | Enable CDC engine & diagnostics frame.                 |

```bash
# QUIC mode (default, recommended)
./zig-out/bin/geoded --listen-quic 0.0.0.0:7567

# QUIC is the only network transport; stdio remains available via `--stdio`.

# With persistent storage
./zig-out/bin/geoded --data_dir ./data --listen-quic 0.0.0.0:7567
```

````bash

When using stdio mode (default), pass flags to the spawned server via repeated `--server-arg` parameters. This is useful to control `--data_dir` or feature flags without starting the server yourself:

```bash
````

### QUIC Smokes and Transport Parity (Optional)

The QUIC transport is experimental and gated in tests. To run the optional QUIC smokes and stdio↔QUIC transport parity tests locally:

```bash

# 3) Run all gated transport parity tests (non-fatal bundle)

# Notes:
# - Tests enable passive teardown for QUIC via GEODE_QUIC_PASSIVE_TEARDOWN=1 to reduce flakiness.
# - Default test runs skip QUIC tests unless GEODE_CI_QUIC_SMOKE is set.
```

Run a single transport parity test manually:

```bash
GEODE_CI_QUIC_SMOKE=1 zig test tests/e2e_protocol_transport_parity_case.zig
```

Curated varlen dataset parity (manual):

```bash
# Prepare: short-lived QUIC server over curated dataset
GEODE_QUIC_PASSIVE_TEARDOWN=1 ./zig-out/bin/geoded \
  --listen-quic 127.0.0.1:17671 --log_json --result-format json \
  --test-exit-after-first-request --data_dir ./data/varlen_determinism &
sleep 0.4

# Stdio vs QUIC runs should emit identical BINDINGS rows
Q='MATCH (a:Person)-[:KNOWS*1..2]->(b:Person) RETURN a.name AS a, b.name AS b ORDER BY a, b LIMIT 6'
STDIO=$(./zig-out/bin/geodec "$Q" --format json --server-arg --data_dir --server-arg ./data/varlen_determinism)
QUIC=$(./zig-out/bin/geodec "$Q" --server 127.0.0.1:17671 --quic --format json)
echo "$STDIO" | grep '"type":"BINDINGS"' > /tmp/stdio_rows.json
echo "$QUIC" | grep '"type":"BINDINGS"' > /tmp/quic_rows.json
diff -u /tmp/stdio_rows.json /tmp/quic_rows.json && echo "Rows match"
```

### Nightly Transport Parity Summary

The nightly workflow (`nightly-transport-parity.yml`) runs the full set of gated transport parity smokes under strict mode and publishes two artifacts:

1. `parity-artifacts` — Raw stdout/stderr logs and binaries snapshot.
2. `parity-summary` — JSON Lines file (`parity-summary.jsonl`) containing per-test row hash summaries:

Example line:

```json
{
  "test": "e2e_protocol_transport_parity_varlen_dataset_rows.zig",
  "rows_sha256": "1b4f2a...",
  "status": "OK"
}
```

Usage:

```bash
# After downloading parity-summary.jsonl
jq -c 'select(.status=="FAIL")' parity-summary.jsonl  # list any failed/parity-mismatched tests
cut -d ' ' -f2 parity-summary.jsonl | sort | uniq -c    # quick distribution of hashes
```

If a test unexpectedly changes output determinism, its hash will differ versus prior runs (compare artifacts); investigate planner/executor ordering logic, tie-break policy (UA005/UA006), or result pagination. Server arg passthrough (`--server-arg`) ensures stdio path can mirror dataset flags used by QUIC server for apples-to-apples comparisons.

#### Parity Summary Diff (Historical Comparison)

The helper script `scripts/parity_summary_diff.sh` compares a previous `parity-summary.jsonl` with the current one and emits JSON Lines of type `ADDED`, `REMOVED`, or `CHANGED` (hash differences). Nightly workflow will generate a diff automatically if `PARITY_PREV_SUMMARY` is provided (e.g., via a retained artifact). Manual usage:

```bash
bash scripts/parity_summary.sh                    # generate current parity-summary.jsonl
cp old/parity-summary.jsonl prev.jsonl            # retrieved earlier artifact
bash scripts/parity_summary_diff.sh prev.jsonl parity-summary.jsonl > diff.jsonl
grep 'CHANGED' diff.jsonl
```

Guard Test: `tests/e2e_parity_summary_guard.zig` ensures every parity test has a summary row when the summary file is present (skips locally if missing). This prevents silently untracked tests as new parity cases are added.

##### Parity Summary Diff Guard (New)

A complementary governance test `tests/e2e_parity_summary_diff_guard.zig` enforces that:

1. No `REMOVED` entries appear in `parity-summary-diff.jsonl` (removal is treated as a regression until explicitly justified by deleting the underlying test).
2. The count of `CHANGED` entries does not exceed a configurable threshold (default 0) to catch unexpected determinism drift.

Environment variable:

| Variable                   | Effect                                                  |
| -------------------------- | ------------------------------------------------------- |
| `GEODE_PARITY_CHANGED_MAX` | Maximum allowed `CHANGED` entries in diff (default: 0). |

Behavior:

- If `parity-summary-diff.jsonl` is absent (e.g., local dev without historical artifact) the guard test skips.
- To intentionally allow limited churn (e.g., refactor touching ordering), set `GEODE_PARITY_CHANGED_MAX` to the number of expected changed hashes for that run.
- Any `REMOVED` entry fails immediately (require adding back test or updating expectations).

Example (allow up to 2 legitimate deterministic changes during a refactor):

```bash
GEODE_PARITY_CHANGED_MAX=2 zig build test -Doptimize=ReleaseSafe
```

CI Integration Suggestion: pass `GEODE_PARITY_CHANGED_MAX=0` in nightly to maintain strict regression sensitivity; raise only in a temporary maintenance branch with explicit review.

## Profiling & Metrics

Use the `PROFILE` prefix before a GQL query (via server line protocol or `geodec`) to emit a PROFILE frame. The first frame is SCHEMA; the second contains JSON with:

`op`, `input_rows`, `rows`, `time_ns`, `cumulative_time_ns`
`bytes_out`, `bytes_alloc`
`estimate_bytes`, `estimate_vs_actual`
`percent_peak`, `percent_net`

### Env Vars (runtime policies, spills, profiling)

| Variable                      | Effect                                                                 |
| ----------------------------- | ---------------------------------------------------------------------- |
| `GEODE_NULLS_LAST`            | Switch ORDER BY null ordering from default nulls-first to nulls-last.  |
| `GEODE_SPILL_THRESHOLD_BYTES` | When peak_bytes >= threshold, mark spill counters (sort/distinct).     |
| `GEODE_FORCE_SORT_SPILL`      | Force `sort_spills` = 1 (spill_reason=forced).                         |
| `GEODE_FORCE_DISTINCT_SPILL`  | Force `distinct_spills` = 1 (spill_reason=forced).                     |
| `GEODE_FORCE_UNION_SPILL`     | Force `union_spills` = 1 (spill_reason=forced).                        |
| `GEODE_PROFILE_MEMCURVE`      | Enable `mem_curve` emission (alternative to CLI `--profile-memcurve`). |
| `GEODE_WAL_COMPACT_INTERVAL`  | Trigger WAL compaction every N commits (default: 5).                   |

### WAL Compaction Tool

`wal_compact` reclaims obsolete WAL segment files.

Usage:

```bash
zig build tools      # build auxiliary tools
./zig-out/bin/wal_compact --base /path/to/data/geode_wal --auto
```

Options:

- `--base <path>`: Prefix path used when WAL was opened (without `.wal.N`).
- `--auto`: Scan segments to find last checkpoint LSN and compact using that durable boundary.
- `--durable-lsn N`: Explicit durable LSN boundary (numeric) instead of auto scan.

Example flow:

1. Database emits periodic checkpoints (via internal `writeCheckpoint`).
2. Run `wal_compact --auto` after a checkpoint + data flush to reclaim older segments.

Safety: Active segment (currently open for append) is not deleted even if below durable boundary. Future versions may add a rotation+compact combined command.

### CLI Profiling Flags

| Flag                 | Effect                                     |
| -------------------- | ------------------------------------------ |
| `--no-estimates`     | Suppress planner estimate & error fields.  |
| `--profile-compact`  | Omit zero-value optional metrics.          |
| `--profile-memcurve` | Emit `mem_curve` points (same as env var). |

Percentage metrics (`estimate_vs_actual`, `error_abs_pct`) are capped at 999 for stability.

### Example


### Benchmark Regression Check

Compare current benchmark run against a stored baseline with tolerance (default 15% increase allowed):

````bash
zig build tools
zig build test 2>&1 | ./zig-out/bin/bench_extract > bench_current.jsonl
./zig-out/bin/bench_regress benchmarks/baseline.jsonl bench_current.jsonl 15

Outputs a single JSON summary line to stdout:

```json
{"type":"bench_regress_summary","baseline":"benchmarks/baseline.jsonl","current":"bench_current.jsonl","tolerance_pct":15,"compared":6,"regressions":0,"regression_keys":[],"ts_ms":1730000000000}
````

Fields:

- `compared`: total metric comparisons (kind \* metric_name) excluding timestamps.
- `regressions`: count of failing comparisons.
- `regression_keys`: array of `kind:metric` identifiers that failed.
- `tolerance_pct`: applied tolerance for increases (only increases currently considered). Value is the nearest integer rounding of the user-supplied (or default) tolerance argument.

Multi-metric: any numeric field parsed (e.g. `elapsed_ns`, `total_bytes`, `allocs`). Timestamp fields like `ts_ms` are ignored.

Baseline refresh (write current metrics as new baseline):

```bash
./zig-out/bin/bench_regress benchmarks/baseline.jsonl bench_current.jsonl 15 --write-baseline benchmarks/baseline_new.jsonl
# Refuses if regressions detected; override with --force
./zig-out/bin/bench_regress benchmarks/baseline.jsonl bench_current.jsonl 15 --write-baseline benchmarks/baseline.jsonl --force
```

CI Suggestion: capture summary line and parse `regressions` > 0 for failure gating or attach as artifact.

```text
Return code non-zero (RegressionDetected) signals a regression beyond tolerance for at least one metric's `elapsed_ns`.
```

## Stability & Fuzz Coverage

- PROFILE / EXPLAIN schema frozen at `profile_version=2`. Any structural key additions or removals REQUIRE incrementing this version and updating snapshot signatures.
- Decimal ordering correctness validated by a 10k pair randomized fuzz harness (`e2e_protocol_decimal_fuzz.zig`) covering mixed int/decimal scales and ensuring transitive comparator semantics.
- Comparator invariants: antisymmetry, transitivity, and total ordering over (int, decimal) domain with scale normalization. Violations would panic in fuzz; current corpus passes.
- Version bump policy: (1) modify schema, (2) update freeze tests (`e2e_protocol_profile_explain_freeze.zig`), (3) bump `profile_version`, (4) regenerate README example if changed.
- Future extensions (counting allocator, HashAgg) will NOT alter existing keys; additions append optional fields gated by version bump if structural.

### Snapshot & Test Workflow

Snapshot tests assert structural stability of PROFILE output while tolerating numeric variance.

Implemented snapshot layers:

- Baseline structural signature (`e2e_protocol_profile_snapshot.zig`)
- mem_curve presence/prefix (`e2e_protocol_profile_memcurve_snapshot.zig`)
- Estimates suppression (`e2e_protocol_profile_no_estimates_snapshot.zig`)
- Spill reasons (forced & threshold) tests
- Allocation delta & op ordering invariants (`e2e_protocol_profile_alloc_deltas.zig`)

Signature Generation / Update:

1. Run `zig build test` after intentional PROFILE schema change.
2. Failing snapshot test prints `SNAPSHOT_SIGNATURE=...`.
3. Replace the `EXPECTED_SIGNATURE` constant in the snapshot test with the printed value.
4. Commit new snapshot along with schema change; bump `profile_version` if shape changed.

Normalization Rules:

- All digit sequences (including decimals) collapsed to '0'.
- Whitespace removed.
- Order of keys preserved; new keys require version bump.

Allocation Deltas:

- Per-stage `bytes_alloc` derived from net allocator snapshots at each stage boundary (delta from previous boundary).
- `percent_peak` / `percent_net` computed from these deltas, not cumulative sums.

Spill Reason Semantics:

- `forced` when an explicit `GEODE_FORCE_*` env var triggers spill counters.
- `threshold` when `GEODE_SPILL_THRESHOLD_BYTES` <= peak_bytes and no explicit force provided.

Updating Tests for New Ops:

- Add new op to ordering validation allowlist in `e2e_protocol_profile_alloc_deltas.zig` (maintain monotonic order).
- Update snapshot signature after confirming stable normalized output.

## Numeric Promotion Matrix (REQ-GQL-013)

Geode implements ISO/IEC 39075:2024 numeric type coercion with the following promotion rules:

### Type Precedence (lowest to highest)

1. **Int** (64-bit signed integer)
2. **Decimal** (128-bit coefficient with scale)
3. **Float** (64-bit IEEE 754)

### Promotion Rules

| From    | To      | Valid? | Lossy? | Notes                                   |
| ------- | ------- | ------ | ------ | --------------------------------------- |
| Int     | Decimal | ✓      | ✗      | Always safe, scales coefficient by 10^n |
| Int     | Float   | ✓      | ✗      | Safe for values within float precision  |
| Decimal | Int     | ✓      | ✓      | Truncates fractional part               |
| Decimal | Float   | ✓      | ✓      | May lose precision for large decimals   |
| Float   | Int     | ✓      | ✓      | Truncates fractional part               |
| Float   | Decimal | ✓      | ✓      | May lose precision at extremes          |

### Operation Result Types

- **Addition/Subtraction**: Result type is the higher precedence operand type
- **Multiplication**: Result type is the higher precedence operand type
- **Division**: Result type is at least Decimal (Int÷Int→Decimal for precision)
- **Comparison**: All numeric types are comparable through promotion

### Division by Zero Handling

Division by zero operations emit `TypeMismatch.DivZero` diagnostic (ISO 16.x) instead of runtime panic.

```gql
RETURN 1/0  -- Emits TypeMismatch.DivZero with status_class 22000
```

### Implementation-Defined Policies

- **I:NumericPromotion**: Int→Decimal widening preserves exact value
- **I:DecimalScale**: Default scale is 2 for division results
- **I:FloatPrecision**: IEEE 754 double precision (53-bit mantissa)

## Diagnostics (policy and ISO anchors)

| Code                 | Meaning                                                    | ISO anchor  | Example                        |
| -------------------- | ---------------------------------------------------------- | ----------- | ------------------------------ |
| US001                | LIMIT/OFFSET on unordered table (requires stable ORDER BY) | 16.18–16.19 | RETURN 1 LIMIT 10 OFFSET 5     |
| IllegalOrderKey      | ORDER BY key must be identifier (policy: ident-only)       | 14.10       | RETURN a ORDER BY f(a)         |
| GroupByIllegal       | Invalid GROUP BY legality (e.g., non-aggregated columns)   | 14.10       | RETURN a, SUM(b) GROUP BY a, b |
| TypeMismatch         | Illegal cross-type comparison/ordering                     | 16.x        | RETURN 1 < "2"                 |
| TypeMismatch.DivZero | Division by zero operation                                 | 16.x        | RETURN 1/0                     |
| TxnState             | Transaction state error (invalid lifecycle transition)     | 8           | COMMIT without BEGIN           |
| StoragePageChecksum  | Page checksum mismatch during storage operations           | 4           | Corrupted page detected        |

The CLI and server surface diagnostics with status_class/subclass per ISO 23.2. Tests assert codes/anchors via stderr.
