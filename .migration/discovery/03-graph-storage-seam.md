# seam:graph-storage-in-geode

## summary

DEFINITIVE, FULLY-VERIFIED answer. geode consumes the external `graph-storage` library as a FETCHED git dependency (NOT a path dep), resolved EAGERLY via b.dependency, exposed under module name `graph_storage`, imported into the geode root module + the `geode` executable + the `graph_store` sub-module + several test/bench modules, and wrapped by `src/storage/graph_storage_adapter.zig` whose `StorageAdapter` struct owns a name->engine map of `ManagedGraph` (each wrapping one `gs.ShardedGraphEngine`). The runtime instance is a process-global `?*StorageAdapter` in `src/graph_store.zig`, created by `initGlobalAdapter` and reachable via `getGlobalAdapter`. This is the exact template the two new libs must mirror.

## perf_notes

build.zig.zon:334-338 documents the external engine (gs.ShardedGraphEngine) as N=16 single-threaded shards, per-shard WAL/manifest, 2PC cross-shard edges, parallel per-shard crash recovery; microbench-verified >=4x throughput vs single-engine at 16 cores. The adapter layers a 64-shard exact node-property index (exact_node_property_index_shard_count=64, lines 36/89-120) so high-parallel MERGE/property writes don't serialize on one global StringHashMap mutex (CANARY REQ-QUIC-HC-122). Lock hold-time is a tracked perf gate via tests/test_graph_storage_adapter_metrics.zig ('Hold-time atomics unit test', build.zig:4630) plus g_exact_node_property_lookup_count / g_label_scan_lookup_count atomics (lines 32-60) and ManagedGraph.rwlock_shared_hold_ns_total timing. CLAUDE.md GAP-0278 mandates lock order graph_handles_mutex (tier0, brief registry lookups only, never held during data ops) -> per-graph rwlock (tier1); the StorageAdapter exposes per-shard, whole-graph-exclusive, and alphabetical multi-graph lock acquisition to honor this. ManagedGraph pointers are heap-allocated and stable once created (graphs are not removed mid-run), so callers resolve the pointer under a brief mutex hold then operate under the per-graph/per-shard rwlock.

## risks

- Dep-key vs repo-name mismatch: build.zig.zon key AND @import module name are `graph_storage` (underscore) while the git repo is `graph-storage` (hyphen). The two new libs must use the underscore form for the zon key + b.dependency() + @import, or resolution/import fails.
- Eager vs lazy: graph_storage is EAGER (b.dependency, no .lazy). Making a new lib optional changes BOTH the zon (.lazy = true) and build.zig (b.lazyDependency returns an optional to unwrap). Default to eager to match.
- addImport fan-out: graph_storage is imported into 7 modules/targets; omitting any only fails that target. New libs need at minimum root_mod (734 group) + geode_exe (795 group), plus graph_store_mod/tests if consumed there.
- Module-dedup diamonds: build.zig has many 'file exists in modules X and X0' mitigations (gql/otel option forwarding, shard_worker_tls / runtime_metrics / query_ast_cache promoted to named modules). If a new lib shares a transitive dep with geode, forward identical build options.
- Global-singleton ownership: the runtime adapter is a process-global (graph_store.zig:6734). A new lib that mirrors this must follow geode's pattern of an init/getGlobal/deinit trio and ensure deinit is actually called on shutdown to avoid leaks (CLAUDE.md requires zero leaks in tests).
