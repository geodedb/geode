ARCHITECTURE / PERSISTENCE MODEL (durable on-disk LSM, verified): Write path = append a CRC32C-protected record to a WAL (delegated to the external `wal` library, opened with manual_sync=true) AND insert into a 16-shard in-memory Memtable. When the memtable hits `max_memtable_points` (default 100_000) it rotates into a flushing slot and a thread_pool background worker encodes its points to Gorilla-compressed blocks in an immutable on-disk SEGMENT file (TSSEG002 plaintext / TSSEG003 AES-256-GCM). A double-buffered (manifest.a/manifest.b ping-pong, CRC32C-verified, atomic rename) MANIFEST tracks the live SegmentMeta list, next_segment_id, last_checkpoint_lsn, and ts_uuid. Background COMPACTION merges L0→L1 (threshold 4) and L1→L2 (threshold 8) to bound read amplification. A per-engine bounded LRU SegmentReaderCache (default 64 open FDs, refcounted, mutex-guarded, invalidated on compaction) avoids reopening segment files. Backup (checkpoint/snapshot/restore) and on-disk format MIGRATION (TSSEG001→V2/V3, footer rewrites) exist. Optional transparent at-rest encryption (single 32-byte AES-256-GCM key covering WAL + segments + manifest, with AAD domain separation "seg"/"mnf"). So: in-memory memtable + WAL journal + immutable segment files + manifest + background flush/compaction + LRU reader cache + optional TDE. There is NO mmap; segment reads are file reads via SegmentReader.

DATA MODEL (types.zig, verified): `Point = struct { ts: i64, value: i64 }` — VALUES ARE i64 INTEGERS (not f64). `ts` is a caller-chosen OPAQUE monotonic i64; the engine never reads a clock, assumes no epoch/unit (ms-since-Unix-epoch is only an interop convention). Mixing units within a series silently breaks range queries, segment min/max pruning, and Gorilla delta-of-delta. `SeriesId = u128`. Series are addressed by the u128 id; there is NO tag/label/metric-name model in the core — identity is the u128. `opaqueSeriesId(tenant:u64, app_key:u64, key:[32]u8) SeriesId` derives an unguessable id via HMAC-SHA256[key, tenant_le||app_key_le](0..16) (GAP-0002/SEC-008).

DURABILITY / RECOVERY (verified): `DurabilityMode = enum { batch, per_call }` — batch (default): appendPoints does NOT fsync; a background syncer thread fsyncs every wal_sync_interval_ms (up to that much data-loss window). per_call: fsync before appendPoints returns (crash-safe fence). `WalRecoveryPolicy = enum { fail_closed, salvage }` — fail_closed (default) aborts Engine.init on any WAL deserialise failure / CRC32C mismatch (error.InvalidFormat / error.ChecksumMismatch); salvage = best-effort lossy readFrom (forensic). CONCURRENCY (verified): multithreaded. Engine.init takes `*thread_pool.ThreadPool` (borrowed) used for background flush + compaction; a separate syncer std.Thread handles batch fsync. appendPoints/flush/queryPoints/sync are thread-safe (engine std.Io.Mutex `mu` + done_cv condition). active_mem is an atomic *Memtable; writers snapshot it lock-free, bump the memtable's pending_writers barrier, and insert without holding mu (P-LOCK-005). ## risks

- TASK PREMISE INVALID: the three named files do not exist. Real paths are src/root.zig (API root), tests/integration.zig + tests/engine_e2e.zig, benchmarks/bench.zig. The repo is a durable multi-file LSM engine (WAL + segments + manifest + L0/L1/L2 compaction + 16-shard memtable + thread pool + optional AES-256-GCM TDE + backup + migration), NOT a single-file in-memory store. Point.value is i64 (integer), NOT f64. Version is 0.2.0, NOT 0.1.0. Deps are wal/uuid/thread_pool, NOT zero. Any documentation written to the task's assumptions would be materially wrong.
- STALE TEST: tests/integration.zig:25 asserts lib.version == "0.1.0" while the library declares "0.2.0" (root.zig:29, build.zig.zon:3). The integration suite's version test is out of sync with the shipped version.
- TIMESTAMP-UNIT FOOTGUN (types.zig): the engine never validates units/epoch on Point.ts; mixing units within a single series silently corrupts range queries, segment min/max pruning, and Gorilla delta-of-delta. Caller must enforce one monotonic unit per series.
- BATCH durability (default) has a data-loss window of up to wal_sync_interval_ms (100ms default) on crash; callers needing a per-append durability fence must set durability_mode=.per_call.
- Engine.deinit must NOT run concurrently with any other engine op (explicitly documented). data_dir is NOT created by the engine — caller must mkdir first or Engine.init returns error.FileNotFound.
- Encryption key must stay consistent across opens; reopening with a different/absent key fails closed (DecryptionFailed / dropped WAL records). Key rotation requires an external read-and-re-encrypt migration (not provided by the engine).
- compare-bench regression thresholds live in benchmarks/compare.zig (not line-read this run); the numeric pass/fail gate values are therefore not captured here. tests/wal_recovery.zig and tests/stress.zig and src/main.zig (CLI) were not line-read (behavior inferred from build steps + WalRecoveryPolicy doc).
